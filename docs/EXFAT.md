# Native FAT32 and exFAT support

Anvil has target-neutral FAT32 and exFAT 1.x filesystems behind one
block-device seam and one filesystem facade. Board code supplies 512-byte block read,
write, and optional flush callbacks; the filesystem contains no USB, SD,
firmware, or chip-specific logic.

## Supported surface

- raw exFAT volumes, MBR type-07 partitions, and CRC-validated GPT Microsoft
  Basic Data partitions
- 512, 1024, 2048, and 4096-byte logical sectors and clusters through 32 MiB
- active FAT and allocation bitmap, free-space accounting, and bounds checks
- main and backup boot-region validation
- nested directory traversal
- UTF-8 paths, strict UTF-16 decoding, the volume up-case table, case-insensitive
  lookup, long names, name hashes, and entry-set checksums
- read, write, create, extend, truncate, rename, and remove for files
- create, enumerate, rename, and remove for directories
- timestamps, metadata preservation during rename, flush, and clean unmount

FAT32 (`Anvil/Storage/fat32.pbi`) has the same surface since 2026-09-17 (forum
898): folders at any depth, long (VFAT) names read and written with the short
alias generated by the specification's basis-name and `~N` numeric-tail rules,
case-insensitive lookup by long or short name, create, write, extend, truncate,
rename and move, `mkdir`, removal of a file or an EMPTY folder, FSInfo, and the
FAT[1] clean-shutdown bit. Until then it was root-only and 8.3-only.

## Partitions and paths

`Anvil/Storage/filesystem.pbi` is the only layer that picks a filesystem. A
medium may carry up to four MBR partitions, and every FAT32 or exFAT one is
reachable. A path names its partition with a digit and a colon:

| Path | Means |
|---|---|
| `2:/exfat test/random-1MiB.bin` | that file on partition 2 |
| `2:hello.txt` | the same as `2:/hello.txt` |
| `KERNEL8.IMG` | partition 1 - a path with no prefix is **always** partition 1 |

The prefix is stateless on purpose: a data partition used a moment ago can
never capture a later unprefixed `save KERNEL8.IMG`. The colon cannot occur in
a FAT or exFAT name. On a GPT disk the digit is the Nth Microsoft Basic Data
entry.

One volume is mounted at a time. A path on another partition unmounts the
current volume cleanly and mounts its own; mounting only reads. An open file
refuses the switch. `f` lists each partition in the table with its format,
cluster size, size and start block, or the filesystem's own refusal.

`load`, `save`, `ls`, `cat`, `mkdir`, `rm` (`del`), `rmdir` and `rename`
(`mv`) accept these paths, on FAT32 and exFAT alike. Enclose paths containing
spaces in double quotes. The monitor line editor accepts the full 1023-byte
path limit. `rm` removes one file or one empty directory and nothing
recursive; `rmdir` removes one empty directory and refuses a file. A rename
may change only the case of a name. Volume errors 3 and 4 (FAT root-only)
are retired and no longer raised.

The facade reports which layer failed (`FsErrorKind()`), and callers ask
`FsErrorIsNotFound()` / `FsErrorIsNoWriter()` rather than comparing numbers:
the FAT and exFAT drivers number their errors independently.

## Safety behavior

Read-only mount and unmount never write. Before the first change of any kind -
including an overwrite that allocates nothing (forum 902) - exFAT marks a
previously clean volume dirty in the MAIN boot sector only (the Backup Boot
Region is never written, specification section 3 and 3.1.13; forum 903), and
FAT32 clears the ClnShutBitMask bit of FAT[1] in every live FAT copy (forum
901). Flush asks the device to commit its cache (SCSI SYNCHRONIZE CACHE on the
USB stick), then sets the volume clean - exFAT also brings PercentInUse up to
date or sets it to FFh (3.1.18; forum 904) - and flushes again. A volume that
was already dirty when mounted stays dirty: exFAT refuses to change it, FAT32
changes it and leaves the mark for a disk check. After a block read or write
fails in the middle of a change the dirty mark is kept.

The order of writes keeps every interruption repairable without losing data:

| Operation | Order | An interruption leaves at worst |
|---|---|---|
| grow a file | clusters claimed, data written, directory entry updated last | lost clusters |
| shrink, remove | directory entry first, clusters freed after | lost clusters |
| FAT32 create | long-name entries, then the short entry, each sector written once | orphaned long-name entries |
| FAT32 remove | the short entry's sector first (with any long-name entries in it), then the rest of the run (forum 894) | orphaned long-name entries |
| exFAT create | the whole entry set in one sector write; a set spanning sectors marks its file-entry slot unused first (forum 914) | orphaned stream / name entries |
| exFAT update | the file and stream entries rebuilt in memory with their checksum and written once when they share a sector (forum 909) | the old or the new set |
| exFAT remove | the file entry first (forum 908) | orphaned stream / name entries |
| folder growth, mkdir | the new cluster claimed and ZEROED before anything points at it | lost clusters |
| rename, move | the new entry first, a moved FAT32 folder's `..` next, the old entry removed last | two names for one object (reported as cross-linked) |
| a write refused for lack of space | every cluster it claimed given back, the old end of chain restored (forums 900, 907) | nothing |

A FAT32 file is refused past 4,294,967,295 bytes before anything is allocated
(forum 899). exFAT reads return zeros past a file's ValidDataLength up to its
size, and a write that starts past ValidDataLength zeros the gap first (7.6.4;
forum 906). `.` and `..` are refused as names on both (7.7.3; forum 905). A
directory ends at an end-of-directory entry or at the end of its clusters
(forum 913).

**Timestamps (forum 911).** Before each change the monitor hands the
filesystems the wall-clock time when it is TRUSTED (set by hand or by SNTP), as
local time with the zone offset, and otherwise the formats' first instant,
1980-01-01 00:00:00. FAT32: `DIR_CrtDate`, `DIR_CrtTime`, `DIR_CrtTimeTenth`
and `DIR_LstAccDate` on creation, `DIR_WrtDate`, `DIR_WrtTime` and
`DIR_LstAccDate` on every write. exFAT: `CreateTimestamp`,
`LastModifiedTimestamp`, `LastAccessedTimestamp`, both 10 ms fields and all
three `UtcOffset` fields (OffsetValid set, 15-minute steps) on creation;
`LastModifiedTimestamp`, `LastAccessedTimestamp`, `LastModified10msIncrement`
and their offsets on every write; an unset clock writes UtcOffset 0 (not
valid). A rename keeps the times. A write or rename sets the ARCHIVE attribute
(forum 912). Malformed geometry, checksums, names, chains,
allocation, or out-of-volume references are refused with a numbered sentence.

Two-FAT volumes are TexFAT. Anvil selects the active FAT and bitmap for
read-only inspection but refuses changes because it does not implement TexFAT
transactions. Formatting and filesystem repair are intentionally outside this
driver.

## Verification status

### The file-operation gate, 2026-09-17

`python tools/fileops_check.py --compiler <PureMetalForge.exe>` formats a disk
with an MBR, a FAT32 partition (65,920 clusters of 512 bytes) and an exFAT
partition (4,089 clusters of 4,096 bytes) using `tools/fs_reference.py`, an
independent implementation that shares no code with `Anvil/Storage`, and puts
on it what a PC would leave: a long-named file, a file whose ValidDataLength
is short of its size, free space full of old bytes, and a filler file that
leaves each volume nearly full. The real drivers are compiled into a program
that runs 163 operations per filesystem against that disk on the A64 model:
create; write, overwrite, append and truncate across cluster boundaries and at
exact cluster multiples; zero-length files; folders two deep; a folder grown
past one cluster by 50 long-named files; long and Unicode names looked up in
another case; short-alias collisions (`LONGFI~2.TXT`); renames in place,
case-only, across folders and of a folder, and a folder moved into itself
refused; removal of long-named files and of a non-empty and a non-folder
target refused; `.`, `..` and `:` refused; the 4 GiB ceiling; a write that
fills the volume; timestamps with and without a trusted clock; an inherited
dirty mark; and a remount.

The harness then reads the medium with `fs_reference.py`, asking the drivers
nothing, and requires no errors, no leftovers, clean flags, free counts equal
to the allocation, untouched boot and backup regions, and a tree equal name
for name and byte for byte to its own model. Finally it replays the recorded
sector writes onto the starting disk one at a time and checks the volume after
every one: an interruption may leave only what the table above allows, and
never while the volume says it is clean.

| | FAT32 | exFAT |
|---|---|---|
| operations | 163, all as required | 163, all as required |
| sector writes / power-cut states checked | 3,580 / 3,578 | 6,186 / 6,184 |
| final medium | clean, exact | clean, exact |
| dosfstools `fsck.fat -n -V` on the finished partition | clean | not available (see below) |

`--mutate` re-runs the gate with one defect at a time. Every fix above has a
mutant, and every mutant is caught.

The desk proof has one external checker. dosfstools' `fsck.fat` read the
finished FAT32 partition clean. No exFAT checker is installed on any machine
this was run on (`fsck.exfat` is absent, and `chkdsk` needs an elevated
prompt to attach an image), so the finished exFAT image is kept for a
`chkdsk` run and the specification-level checks in `fs_reference.py` stand in
until then.

The existing gates were brought up to date and pass: `tools/a64/a64_fat_check.py`
(383 assertions, 13 of 13 mutants), `tools/exfat_fixture_check.py`,
`tools/fat_readat_emitted_check.py` (red since 2026-09-16 and repaired),
`tools/fat_shared_equivalence_check.py`, `tools/a64/a64_settings_check.py`,
`tools/pi3_update_check.py` and `tools/datapath_emitted_check.py`.

### The exFAT fixture gate

The repository includes `RaspberryPi4/Tests/exfat_emitted_gate.pi4` and
`tools/exfat_fixture_check.py`. They compile the production driver with the
unified IDE's headless mode and execute the emitted A64 against a writable
memory volume. The gate covers read-only behavior, dirty-volume refusal, MBR
and GPT discovery, Unicode and folded lookup, nested directory growth, the
file/directory mutation lifecycle, flush/unmount/remount persistence,
free-space restoration, rename-cycle rejection, and damaged metadata refusal.
Its facade section moves the volume to MBR slot 2 and proves `N:` paths reach
it, an unprefixed path does not, a cross-partition rename and an empty path
are refused, and one read of a nine-cluster FAT-chained file costs at most one
FAT lookup per cluster.

Reading from exFAT was as fast as reading from FAT32 because both were
limited by one-block USB mass-storage transfers (forum 895). **Writing was
about 30 times slower than reading** (forum 893): every new cluster was zeroed
before the data was written over it, and every sector was read before it was
written - and on this stick a read between two single-block writes costs about
4 ms per write (1 MiB to FAT32: 0.86 s written whole, 9.3 s read-modify-write).

The storage speed change of 2026-09-17 removes all of it: READ (10) and
WRITE (10) of up to 1 MiB with the stick's burst size, sector runs through
contiguous clusters in one call, no pre-read and no zeroing of file clusters
(folders are still zeroed), FAT and bitmap changes written a sector at a time
ahead of anything that depends on them, and a one-sector read cache under the
byte-at-a-time metadata reads that made a partition switch cost about 2 s
(forum 897). `tools/fileops_check.py` replays every sector write of it on both
filesystems with the power cut after each one. Board speeds with the change:
not measured yet.

Still not run on the board: refusal of a separately damaged copy, persistence
across a reboot of what was written, and a FAT-chained (fragmented) file. The
chained case is covered by the desk gate.

## Source and specification

The implementation is clean-room code based on Microsoft's public
[exFAT specification](https://learn.microsoft.com/en-us/windows/win32/fileio/exfat-specification)
and the Microsoft EFI FAT32 File System Specification 1.03 ("fatgen103").
No Linux or U-Boot filesystem implementation is included or copied.
