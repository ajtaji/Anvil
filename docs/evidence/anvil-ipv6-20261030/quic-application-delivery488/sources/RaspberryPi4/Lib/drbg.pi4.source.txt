; ======================================================================

;  The notice ships as licenses/BearSSL-LICENSE.txt (release condition).
;
;     XIncludeFile "Anvil/Core/sha256.pbi"   ; REQUIRED, include first
;     XIncludeFile "RaspberryPi4/Lib/hmac.pi4"     ; REQUIRED, include second
;     XIncludeFile "RaspberryPi4/Lib/entropy.pi4"  ; REQUIRED, include third
;     XIncludeFile "RaspberryPi4/Lib/drbg.pi4"
;
;
;  HMAC-DRBG with SHA-256 (NIST SP 800-90A section 10.1.2). This is the
;  generator that would feed every TLS random on this part - the engine
;  only ever sees DRBG output, never the raw entropy source.
;
;  API:
;    DrbgInit(seed.i, slen.i)      instantiate: K = $00*32, V = $01*32,
;                                  then Update(seed). The seed is the
;                                  concatenation of entropy + nonce +
;                                  personalisation THE CALLER HAS
;                                  GATHERED. Returns #DRBG_OK, or
;                                  #DRBG_WARN_SHORT_SEED (instantiated
;                                  but under strength), or a negative
;                                  refusal - SEE THE ENTROPY SECTION.
;    DrbgReseed(seed.i, slen.i)    reseed with fresh entropy. Same
;                                  return values as DrbgInit.
;    DrbgGenerate(dst.i, len.i)    produce len pseudorandom bytes into
;                                  dst and roll the state forward.
;                                  Returns len, or #DRBG_ERR_UNSEEDED
;                                  having written NOTHING.
;    DrbgSeeded()                  1 once instantiated, 0 before
;    DrbgSeedBytes()               how many seed bytes it was given
;    DrbgEntropyAvailable()        1 if this library can obtain entropy
;                                  by itself. IT RETURNS 1 SINCE
;                                  2026-08-28 - see below.
;    DrbgAutoSeed()                instantiate from the BCM2711's own
;                                  hardware RNG, with no seed from the
;                                  caller. THE ROUTINE THIS FILE SPENT
;                                  THREE MONTHS UNABLE TO WRITE.
;    DrbgAutoReseed()              reseed from the same source.
;    DrbgEntropyStatus()           what entropy.pi4 said the last time
;                                  either of those two ran.
;
;  REQUIRES sha256.pi4, hmac.pi4 AND entropy.pi4, INCLUDED BEFORE THIS
;  FILE and in that order: the DRBG is built entirely on HmacKey/
;  HmacBegin/HmacUpdate/HmacEnd, and DrbgAutoSeed is built on
;  EntropyBegin/EntropyWarmupWait/EntropyBytes. A library never includes
;  a library (house rule) - the MAIN file lists sha256, hmac, entropy,
;  then this file. If any is missing, this file fails loudly at compile
;  time, naming the procedure it cannot find. No stub.
;
;  entropy.pi4 IS A NEW REQUIREMENT AS OF 2026-08-28 and it is a real
;  cost: a program that only wants to run the known-answer vectors now
;  has to include a file that touches a peripheral. It was taken
;  anyway, because the alternative is DrbgAutoSeed() living somewhere
;  else, and then the one procedure a caller must NOT get wrong is not
;  in the file whose header explains why. Nothing in entropy.pi4 runs
;  unless DrbgAutoSeed or DrbgAutoReseed is called.
;
;  sha256 already turns EnableExplicit on for the whole program; every
;  variable here is declared, as that pragma requires.
;
;  ======================================================================
;   THE ENTROPY SOURCE EXISTS NOW - 2026-08-28. READ THIS ANYWAY.
;  ======================================================================
;
;  THIS LIBRARY CAN SEED ITSELF ON THIS PART. DrbgAutoSeed() enables the
;  BCM2711's RNG200 hardware random number generator through
;  RaspberryPi4/Lib/entropy.pi4, waits out the warm-up that block
;  documents, takes 48 bytes and instantiates from them.
;
;  IT IS STILL TRUE THAT WHATEVER YOU HAND DrbgInit IS THE WHOLE OF THE
;  UNPREDICTABILITY IN EVERY BYTE THE GENERATOR WILL EVER PRODUCE. That
;  sentence did not stop being true when the source arrived; it just
;  acquired a right answer. If you hand it the same seed twice you get
;  the same TLS keys twice, and nothing in the protocol will notice.
;
;  ======================================================================
;   WHAT THE SEEDING CONTRACT IS, EXACTLY
;  ======================================================================
;
;  DrbgAutoSeed() reads 48 BYTES from the hardware and calls DrbgInit
;  with all 48 as one seed string. The split is:
;
;    32 bytes  ENTROPY INPUT. SP 800-90A section 10.1 and Table 2:
;              HMAC_DRBG with SHA-256 supports a 256-bit security
;              strength, and instantiation requires at least
;              security_strength bits of entropy input. 256 bits is 32
;              bytes, which is #DRBG_SEED_STRENGTH.
;
;    16 bytes  NONCE. SP 800-90A section 8.6.7 allows a nonce of at
;              least security_strength/2 bits from the entropy source.
;              128 bits is 16 bytes.
;
;    0 bytes   PERSONALISATION STRING. There is none, and that is a
;              decision rather than an omission. A personalisation
;              string is meant to be something SPECIFIC TO THIS DEVICE
;              AND THIS INSTANTIATION - a serial number, a MAC address,
;              a boot count - and this file cannot obtain any of those
;              without depending on the mailbox, the Ethernet block or
;              the RTC. A caller that has one gathers its own bytes
;              with EntropyBytes(), appends it, and calls DrbgInit
;              directly; the seed is a byte string and DrbgInit does
;              not care where the pieces came from.
;
;  THE 48 BYTES ARE HASHED TOGETHER BY HMAC_DRBG_Update, so the split
;  above is about WHERE THE REQUIREMENT COMES FROM rather than about
;  the arithmetic - the entropy input and the nonce are concatenated
;  and fed in as one string, which is exactly what SP 800-90A section
;  10.1.2.3 specifies.
;
;  THE SEED BUFFER IS WIPED AFTER USE. secDrbgSeed is zeroed the
;  instant DrbgInit returns. It is BSS on a board with no MMU and no
;  memory protection, so anything that can read memory can read it;
;  wiping does not make that safe, it makes the window short. It is
;  named sec* like K and V so a future scrubber can find it.
;
;  ======================================================================
;   WHAT AUTO-SEEDING DOES *NOT* CHECK, AND WHY THAT IS DELIBERATE
;  ======================================================================
;
;  DrbgAutoSeed() DOES NOT RUN entropy.pi4's STUCK DETECTOR. Collecting
;  the few thousand words that detector wants costs about an eighth of
;  a second of sampling at the block's documented 1 MHz rate, on a path
;  that runs at boot before anything else can happen. Paying that on
;  every boot to catch a fault that is permanent when it happens is the
;  wrong trade.
;
;  WHAT IT RELIES ON INSTEAD, and this is not nothing: DrbgSeedUsable's
;  existing #DRBG_ERR_CONSTSEED check runs over all 48 bytes. A block
;  that is dead, unpowered, held in reset or being read at the wrong
;  address produces a constant, and a constant 48 bytes is refused BY
;  NAME before the DRBG is instantiated. That is the failure that
;  actually happens.
;
;  IT WILL NOT CATCH A BLOCK THAT IS MERELY BAD - biased, short-cycled,
;  or a counter. RUN
;  RaspberryPi4/Examples/Diagnostics/pi4Entropy.pi4 ON THE BOARD ONCE
;  and read what it prints, including the paragraph about what its
;  verdict does not establish. That diagnostic exists so that this
;  shortcut is a considered one rather than a hidden one.
;
;  ======================================================================
;   WHAT THE OLD VERSION OF THIS SECTION SAID, AND WHY IT IS KEPT
;  ======================================================================
;
;  Until 2026-08-28 the block here was seventy lines beginning "THERE IS
;  NO ENTROPY SOURCE HERE", and it ended with a concrete instruction:
;  get RNG_CTRL's offset and enable bit, RNG_STATUS's offset and its
;  FIFO-count field, RNG_FIFO_DATA's offset and the documented warm-up
;  discard FROM A SOURCE YOU CAN CITE; then write DrbgAutoSeed(), make
;  DrbgEntropyAvailable() return 1 in the same commit, and delete the
;  block.
;
;  THAT IS EXACTLY WHAT HAPPENED, and the five numbers came from
;  RaspberryPi4/Reference/rpi-6.12.y_iproc-rng200.c with two more
;  drivers agreeing. entropy.pi4's header carries every citation with a
;  line number.
;
;  ONE THING THE OLD BLOCK GOT WRONG IS WORTH KEEPING. It said the
;  numbers were not in any document in Datasheets/ and concluded they
;  were uncitable. The first half was true - bcm2711-peripherals.pdf
;  really does not contain the RNG200 register map, and that was
;  checked rather than assumed. The second half was the mistake: a
;  register map that is not on the disk can be FETCHED, and the vault's
;  own rule says to fetch it and record it rather than to stop. Three
;  drivers arrived in ten minutes. "I cannot cite this" was the right
;  standard applied to the wrong conclusion, which is the same shape
;  the Reference-sources map records for the mailbox tag.
;
;  THE OTHER WARNING IN THAT BLOCK STILL STANDS AND IS NOT SOFTENED:
;  $FE104000 is real, powered peripheral space, and a read of the wrong
;  offset in a live block returns A NUMBER - not a fault, not a zero
;  you would notice. That number would go straight into a seed and look
;  exactly like entropy. It is why entropy.pi4 cites a line number for
;  every offset instead of a chip family for all of them, and why it
;  spells out how the Pi 3's map overlaps this one.
;
;  AND SO DOES THIS: the ARM generic timer (CNTPCT_EL0, which
;  RaspberryPi4/Lib/timer.pi4 reads) is a counter, and a counter read at
;  boot is roughly the same number every boot. The VideoCore temperature
;  tag in mailbox.pi4 moves by a degree or two. Neither is entropy.
;  Mixing them in ALONGSIDE a real source is fine and even sensible;
;  using either as the source is the constant-seed defect wearing a
;  disguise.
;
;  ======================================================================
;   HOW THIS FILE REFUSES, AND WHY IT REFUSES RATHER THAN COPING
;  ======================================================================
;
;  A DRBG THAT QUIETLY PROCEEDS FROM NO SEED IS THE DEFECT. The RP2350
;  copy's DrbgInit takes any seed at all, including a null pointer and a
;  zero length, and comes back looking successful; the generator then
;  emits a completely deterministic stream that passes every statistical
;  test anybody would think to run on it. THIS COPY WILL NOT DO THAT.
;
;    seed = 0, or slen <= 0        #DRBG_ERR_NOSEED
;                                  NOT instantiated. DrbgSeeded() stays
;                                  0 and DrbgGenerate() refuses.
;
;    every seed byte identical     #DRBG_ERR_CONSTSEED
;                                  NOT instantiated. This is the
;                                  32-zero-bytes case and the
;                                  fill-the-buffer-with-$FF case - the
;                                  two shapes an uninitialised or
;                                  never-populated buffer actually has.
;                                  It cannot catch a subtler constant
;                                  and does not pretend to; it catches
;                                  the two that happen by accident.
;
;    0 < slen < #DRBG_SEED_STRENGTH
;                                  #DRBG_WARN_SHORT_SEED
;                                  INSTANTIATED, and it works. SP
;                                  800-90A section 10.1 asks for at
;                                  least security-strength bits of
;                                  entropy, which is 256 bits - 32
;                                  bytes - for HMAC_DRBG with SHA-256.
;                                  A shorter seed is a real weakness
;                                  but it is the caller's call, not
;                                  this file's, so it is ANNOUNCED
;                                  rather than refused. The published
;                                  known-answer vectors this port is
;                                  gated against include seeds shorter
;                                  than 32 bytes, and a library that
;                                  refused to run its own test vectors
;                                  would be its own kind of wrong.
;
;    otherwise                     #DRBG_OK
;
;  DrbgGenerate() RETURNS #DRBG_ERR_UNSEEDED AND WRITES NOTHING if there
;  has been no successful instantiate. Writing nothing matters: a caller
;  that ignores the return value gets whatever was already in its
;  buffer, which is a bug it can find, instead of a smooth stream of
;  predictable bytes, which is a bug nobody finds.
;
;  ALL REFUSALS ARE NEGATIVE AND DrbgGenerate's SUCCESS VALUE IS A BYTE
;  COUNT, so one comparison separates them.
;
;  ======================================================================
;   THE 64-BIT .i, AND THE COUNTERS THAT ARE NOT HERE
;  ======================================================================
;
;  THERE IS NO 32-BIT WORD ARITHMETIC IN THIS FILE EITHER. HMAC-DRBG is
;  defined over byte strings; K and V are 32-byte buffers, the domain
;  separators are single bytes, and the only numbers are lengths. So
;  there is nothing here for #SHA256_W32 to be applied to. The 64-bit
;  masking work for this stack lives entirely in
;  Anvil/Core/sha256.pbi, whose header carries the account.
;
;  THE SP 800-90A reseed_counter DOES NOT EXIST IN THIS
;  IMPLEMENTATION, and it does not exist in the RP2350, RP2040 or RA4M1
;  copies either - BearSSL's hmac_drbg does not keep one. That is
;  recorded here as a GAP rather than left to be discovered: SP 800-90A
;  section 10.1.2 requires that a generate request after
;  reseed_interval requests returns a reseed-required indication, and
;  nothing in this file will ever return one. It generates forever from
;  one seed. Adding the counter is a real piece of work and it belongs
;  in all four copies at once, not smuggled into the 64-bit port.
;
;  So: there was no 32-bit counter here to mask, which is the honest
;  answer to "what did you do about the DRBG's counters". The offsets
;  and remainders in DrbgGenerate are LENGTHS and want to be
;  machine-width, which on this target they are.
;
;  ======================================================================
;   CONSTANT TIME
;  ======================================================================
;
;  K and V are secret DRBG state (sec-named); every step is an HMAC,
;  which is straight-line, and all control in the generate path is
;  driven by the requested length (public), never by state bytes.
;
;  THE TWO SEED CHECKS ADDED BY THIS PORT DO LOOK AT SEED BYTES, and
;  that is worth being explicit about rather than quiet. The
;  constant-seed test accumulates every byte's difference from the
;  first with OR and tests the accumulator ONCE at the end - the same
;  shape as CtEqual in hmac.pi4 - so it never returns early and its
;  running time depends only on slen. The one branch it does take
;  reveals a single public bit: "this seed was degenerate", which is a
;  bit the caller is being told anyway, in the return value. NO OTHER
;  BRANCH IN THIS FILE LOOKS AT A SECRET.
;
;  As in the rest of this stack the claim is STRUCTURAL, read off the
;  source. No cycle-counting harness exists for this backend.
;
;  ======================================================================
;   WHAT HAS BEEN PROVEN, AND WHAT HAS NOT - 2026-08-25, ENTROPY 2026-08-28
;  ======================================================================
;
;  PROVEN, by known-answer test under the project's own A64 oracle
;  (tools/a64/a64_interp.py) on a real image built by pmfc.exe for
;  -t pi4 at $200000, against the vector set the RP2350/RP2040/RA4M1
;  copies are already gated on so that the four targets stay comparable

;

;    * The same vector without the reseed.

;        f92d4cf99a535b20222a52a68db04c5af6f5ffc7b66a473a37a256bd8d298f9b

;    * DrbgEntropyAvailable() returns 1, in the same change that made

;  NOT PROVEN:

;  #DRBG_SEED_STRENGTH - SP 800-90A section 10.1 / Table 2: HMAC_DRBG

; Hardware entropy provider. Positive already-initialized status is accepted;
; no forced restart discards existing warm-up. Preserve the first failure or
; final byte-count status exactly. No DRBG state or seed buffer is owned here.
Procedure.i HwEntropyAvailable()
  ProcedureReturn 1
EndProcedure

Procedure.i HwEntropyRead(dst.i, n.i)
  Protected st.i
  st = EntropyBegin()
  If st < 0
    ProcedureReturn st
  EndIf
  st = EntropyWarmupWait(#ENTROPY_SPINS)
  If st < 0
    ProcedureReturn st
  EndIf
  ProcedureReturn EntropyBytes(dst, n, #ENTROPY_SPINS)
EndProcedure

XIncludeFile "Anvil/Crypto/drbg_entropy.pbi"
