@CHAPTER Where the engineering notes are
@INTRO Seventy-odd notes sit beside this book. This chapter is the map, arranged by what you are trying to do.

@SECTION Why this chapter exists

This book is the way in. It is not the whole record.

Beside `docs/guide/` there are about seventy engineering notes. Each one
is the account of a single piece of work: what was built, how it was
proven, and - the part that matters most - exactly where its boundary
is. They are written for somebody who already knows the machine, and
several of them exist mainly to stop a future reader from believing
something is finished when it is not.

You do not read them in order. You go to the one that owns the thing you
are touching. This chapter tells you which one that is.

@NOTE Read the STATUS SENTENCE FIRST. Most of these notes open with a
status line, and it is load-bearing: "desk-proven", "not integrated into
a board build", "passed on Pi 4 silicon in builds 98 and 99", "no
hardware run or cold-boot causality claim". The difference between
"proven on a desk" and "proven on a board" has cost this project real
days. The status line is the note telling you which kind of claim
follows.

The remaining `VULKAN_*` notes are dated proofs of individual slices -
descriptor state, sampled state, dynamic render geometry - and are best
read from the compatibility inventory outward.

The current Vulkan conversion boundary is specific. Public draw lists can
snapshot one dynamic scissor per draw. The Pi backend normalizes that rectangle
and changes the V3D clip packet only when needed. Atlas sampling, UV vertices,
push tint, exact source-over blend and one display-DMA presentation are joined
by `vulkanAtlasChromeProof.pi4`; cache ranges are maintained as one batch with
one final barrier. The final build-148 RAM-only Pi 4 run returned exact
x0=0x6C85A0 in 10.2 seconds. Its report records one TFU advance, one bin/render
pair and one display-DMA presentation; the exact report and pixel oracle pass
all 211 checks, and fresh capture sequence 8 is a clean rotated 800x1280
picture. The monitor returned to its prompt with the deadman off and no core
leases, so this scene is now a silicon pass.

The first real adapter dependency is now present too. Neon can publish its
current font's linear CPU RGBA8 raster, exact dimensions and copied glyph UVs
through a read-only contract. A font change invalidates every query until the
next successful ensure. The CPU-only ensure does not run the TFU or V3D and
does not expose or publish the private tiled atlas. It also reserves one opaque
white texel and copies its UV rectangle so boxes and glyphs can share one
sampled+tinted pipeline. Its emitted gate passes 26 source checks, 41 run-time
assertions and five hostile mutation checks.

That refactor and the renderer hook change the returning diagnostic's bytes.
The current tree builds a 977,076-byte PMF with expected report pointer
x0=0x6C85C8. It is desk-green,
but another lane owns the shared Pi 4, so the book does not transfer the older
image's silicon result to those new bytes. The same bounded returning run is
still required after the lease is released.

The persistent Vulkan-backed adapter for Neon's boxes, atlas text, fans,
outlines, line lists and clipping is now desk-green. It keeps its pipeline,
descriptor set, atlas and vertex storage resident, installs one complete
primitive family, and submits once per frame without processor pixel drawing.
Fan and line builders are bounded and lower only into public Vulkan
triangle-list vertices. The real existing panel, menu, list and text widgets
produce 109 quads, 47 draws, 654 vertices and five scissor states; the scene
consumes one present intent and calls display DMA once. The next gate is that
exact frame plus the new primitive shapes and screenshot on the Pi 4, then
clean return on HDMI, DSI, rotation and resize.

@SECTION Where this book lives, and when it has to move

One house rule governs this book itself, and it applies to every public
repository in this family:

@FRAG
Each public repository carries its book in docs/guide/, as chapter
files and as a rendered PDF beside them.

The book is updated in the SAME COMMIT as any change to what a
developer does - a command, a flag, a file name, a printed message, a
procedure, a boundary.

A book that lags the code is a DEFECT, not a chore. It is filed and
fixed like any other.
@ENDFRAG

The reasoning is the same one that runs through the rest of this
repository. A reader who follows a documented command and gets something
else has learned that the documentation lies, and they stop trusting all
of it - including the parts that are right. Stale documentation is worse
than none, because none at least sends people to the source.

So the test for a change is not "did I break a chapter". It is: **would
a developer following this book now do something that does not work?**
If the answer is yes, the book moves in that commit, the PDF is
re-rendered, and both go in together.

@NOTE The command that renders the PDF is in `docs/GUIDE.md`, beside the
chapter index. It takes any folder of these chapter files, so every
book in this family is produced by the one renderer - which is what
stops two books drifting into two formats.

@SECTION The one habit worth copying

Notice what almost every note in this list has in common: it says what
was NOT established. "Desk-proven, not integrated into a board build and
not silicon-proven." "No hardware run or cold-boot causality claim."
"The previous frame gate overstated its coverage."

That is the whole reason the set is usable. A note that only recorded
successes would leave you to discover the boundaries yourself, one board
at a time. If you add a note, write the boundary down first and the
achievement second.
