@CHAPTER Raspberry Pi 5: source bring-up

@INTRO Anvil reached an EL3 `pmf>` prompt on Pi 5 hardware from commit `f385c7b`. That boot used a processor-drawn HDMI console; PCIe/RP1, storage, Ethernet and GPU work still need separate acceptance. Host checks can validate reference device trees without a board.

@SECTION Current boundary

The current Pi 5 monitor is the shared `RaspberryPi4/Board/board.pi4`
composition under `#PMF_CHIP = 2712`, with the Pi 5 EL3 stub in
`RaspberryPi5/Board/armstub8-2712.asm`. The image is linked at `$80000`;
`config.txt` must omit `kernel_address`. `tools/pi5_card_build.py` builds
`ANVIL5.IMG` from an exact commit and checks the card before writing it.
`RaspberryPi5/Boot/board.pi4` is the earlier entry diagnostic, not the full
monitor. The Pi 4 `kernel8.img` and `armstub8.bin` are not Pi 5 substitutes.

The serial capture `Raspberry Pi 5/Serial logs/pi5-boot-20260927-6-f385c7b-FIRST-PROMPT.txt`
in the vault records the EL3 stub, HDMI console and `pmf>` prompt. It also
records SD CMD2 failure and refusal to start PCIe because the RP1 inbound DMA
window was not adopted; USB and Ethernet therefore could not start on that
boot. A later returning PCIe payload completed two xHCI No-Op DMA requests on
silicon, but its monitor integration and remaining gates were parked. This
evidence does not establish working boot storage, network or Pi 5 Vulkan.

The vault's `Raspberry Pi 5/SOURCES.md` identifies the pinned official DTBs,
Linux driver references, and datasheets. Its `RESUME HERE - Pi 5 bring-up paused 2026-09-27.md`
and `HARDWARE-BRINGUP.md` record the board checkpoint and remaining work.
There is no Pi 5 board available for the current review.

@SECTION Check the source device trees

From the Anvil repository root, use the explicit vault paths on this host:

@FRAG
$env:PI5_DTB_DIR = "C:\Embedded Compiler\CompilerEmbedded\Raspberry Pi 5\Boot staging"
py -3 RaspberryPi5/Boot/dtb_contract.py "$env:PI5_DTB_DIR\bcm2712-rpi-5-b.dtb" "$env:PI5_DTB_DIR\bcm2712-d-rpi-5-b.dtb" "$env:PI5_DTB_DIR\bcm2712d0-rpi-5-b.dtb"
py -3 -m unittest discover -s RaspberryPi5/Boot -p test_dtb_contract.py -v
@ENDFRAG

The recorded host run reported `Raspberry Pi 5` and `brcm,bcm2712` for all
three variants, with an RP1 bridge at `/axi/pcie@1000120000/rp1`. It also
resolved `chosen/stdout-path` (`serial10:115200n8`) to the enabled PL011 at
`/soc@107c000000/serial@7d001000`. The source RP1 `serial0` and `serial1`
nodes are disabled, so the first debug UART image must not assume either one.
Six tests pass; corrupt and wrong-board DTBs, invalid early-UART paths,
unmapped UART and disabled WLAN are refused. On another host,
set `PI5_DTB_DIR` to the explicit folder with those three named files before
running the tests.

These are source DTBs. The bootloader may change the selected DTB, especially
memory, reserved areas, and boot data. The current monitor checks the live
tree and reads its memory end, DMA mask and board stepping before using those
values. This preflight remains a host check; the later serial capture is the
boot evidence.
