@CHAPTER The console
@INTRO Every command prints something, on every path, whether it worked or not. If one ever returns to the prompt in silence, that is a fault.
@SECTION The prompt

@FRAG
pmf>
@ENDFRAG

Five ASCII characters, the trailing space included, and no newline after
them.

@NOTE That is a **protocol string**, not decoration. Host tools wait for
exactly those five bytes, and at least one of them matches on the end of
what it has read - so the trailing space is load-bearing. On a board
with an on-screen console the prompt is drawn in bright green, but no
escape sequence is inserted into the stream: the colour is a style byte
attached to the screen grid, and the serial and network paths receive
the plain characters. A tool cannot tell the difference and does not
have to.

@SECTION Messages never land on the command line

The command line carries three things: the prompt, what you type, and the
output of the command you ran. **Nothing else is ever written into it.**
Anything a background service has to say - the network console arming on
a new address, a DHCP lease renewed or dropped, the radio losing the link
or getting it back, a Wi-Fi rekey, the mouse being looked for - is a
**message**, and a message goes to the message log instead, whether or not
you are halfway through typing a line.

On the serial line and the network console, read them with `messages`.
On a board with a screen, the banner's status row also shows the newest
one you have not read, after the clock and the temperature:

@FRAG
2026-09-16 13:40:12 CDT    112 F    2 new messages: Wi-Fi: group key rekeyed.
@ENDFRAG

`messages` prints the log oldest first and marks it read, which clears
the banner within a second. Its first line is for a script. This is the
exact output of the monitor's own code, executed under the desk gate
`tools/console_messages_emitted_check.py`. On a Raspberry Pi 4 running
build 164 the same command answered `messages 2 kept 3 lost 0`, message
#1 being the USB mouse and keyboard search - the sentence that used to
print straight after the first prompt:

@FRAG
pmf> messages
messages 3 kept 4 lost 0
Messages from background services, oldest first. These are never
printed on the command line; this is where they are read.
  #1  at 1 s
      The network console is now listening on:
          192.168.137.1 port 5555, over the wired Ethernet
  #2  at 3 s
      Wi-Fi: group key rekeyed.
  #3  at 4 s
      Wi-Fi: lease renewed, 7200 s
@ENDFRAG

`total` counts every message since start, `kept` the lines still held
(64 at most), and `lost` the lines pushed out to make room. A line with
nothing visible in it is not kept, and a byte that cannot be shown as
itself appears as `\xNN`. Everything
up to the first prompt - the boot log - still prints on every console as
it always did.

@NOTE A command's own output is never a message: what `dhcp`, `wifi join`
or `net` print about the network while you wait for them is their answer.
The rule and how it is built are in `docs/CONSOLE_MESSAGES.md`.

  Type help, or just a question mark, for the list of commands.

@FRAG

`Its crc32 is`.

@SECTION Looking at memory

@FRAG
memory <address> <count>     also dump, md, m
readback <address> <length>
write  <address> <value>     also poke, w
fill   <address> <value> [count]     also mw
copy   <source> <dest> <count>       also cp
compare <first> <second> <count>     also cmp
crc32  <address> <count>     also checksum
sha1sum   <address> <count>
sha256sum <address> <count>
@ENDFRAG

All numbers are **hex**. The memory family takes a width suffix:
`memory.b`, `memory.w`, `memory.l` for 1, 2 and 4 bytes.

@SECTION memory is for a person, readback is for a machine

`memory` prints hex with an ASCII column, at most 4096 bytes a call, and
it goes to **every** console at once - the serial port, the screen and
the network - so all three agree about what was printed. That makes it
exactly as fast as the slowest of them. Every character the monitor
prints is pushed through the serial port at 115,200 baud before the
network console sees it, and a dump spends 78 characters on 16 bytes.
Read back over a gigabit cable it managed **1,729 bytes a second**.

`readback` is the same bytes for a tool. It prints a header, the range
as base64 at 48 bytes a line, and a closing line with the byte count
and a crc32 - the format, as `help` gives it:

@FRAG
readback 57400000 1812000 bytes base64
<64 base64 characters>  ... and 37,750 more ...
readback end 1812000 bytes crc32 A1B2C3D4
@ENDFRAG

**The base64 goes only to the console that typed the command.** Typed
over the network console it leaves by the network at that link's speed
and never touches the serial port; typed on the serial port it goes out
the serial port. The other consoles still see the command and its
closing line - the parts a person can read. There is no length limit
and no default length, the address is not moved by `base`, and Ctrl-C
stops it with `readback stopped after N of M bytes crc32 X`, the count
and checksum of what really went.

@TRAP A reader must check **both** numbers on the closing line. A lost
datagram takes whole base64 lines with it and leaves a stream that still
looks orderly, so the length is the first thing that catches it; a byte
changed on the way keeps the length and fails the crc32. The polynomial
is the one `crc32` uses and the one Python's `zlib.crc32` uses, so the
host's answer is independent of the board's.

Measured on the bench board over the cable, the same host, the ranges
compared byte for byte with the image on disk afterwards:

@FRAG
                          memory (build 148)   readback (build 151)
98,304 bytes              56.823 s             0.262 s
                          24 commands          1 command
1,812,000 bytes           1,048 s (build 142)  1.280 s, 1,383 KB/s
                          443 commands         2 commands
per 4,096 bytes           2.37 s               -
retries                   0                    0
@ENDFRAG

@NOTE Most of the 0.262 s is not the transfer. The reader waits for one
receive timeout on the host before it sends, to clear anything still
arriving from an earlier command, and on a small read that is the larger
part of the time. The megabyte figure is the one that shows the rate.
The caches were on for both `readback` runs, as the board was found.

@SECTION sha256sum, and the hex-digit rules

@FRAG
pmf> sha256sum 400000 18CE24
sha256sum over 1625636 bytes, 00400000 .. 0058CE23 ...
The sha256sum is 85370e48df79c7fe06956c2c47a27fef049b3e475d44cbba6395422df6ab463f
  sha256sum of the same bytes on any other machine gives the same digest, so a
  match proves this range is byte-for-byte what that machine has.
@ENDFRAG

Sixty-four lowercase hex digits, the same as the `sha256sum` tool on any
other machine, so the two compare directly. `sha1sum` gives forty.

Three rules about the numbers, and they matter:

**Sixteen hex digits, and no more.** A number of seventeen or more hex
digits is **refused**, not truncated and not wrapped. The count is of
digits typed, leading zeros included - so `0000000000000400` is fine at
sixteen and one more zero in front is not.

@FRAG
!! that address has more than sixteen hex digits, and sixteen is all
   a 64-bit address can have. Nothing was computed.
@ENDFRAG

@TRAP That message is printed for the **address** only. Give the
**count** seventeen digits and you get this instead:

@FRAG
!! a byte count is required, in hex.
@ENDFRAG

which says a count was missing when in fact one was typed and rejected
for its length. That is a real defect - the over-length flag is checked
for the first argument and not the second - and it is named here so that
if you meet it you know what actually happened.

**Exactly two arguments.** A third is refused by name, with the reason:

@FRAG
sha256sum here takes exactly two arguments, an address and a count.
   U-Boot's has a third that stores the digest in memory; it is not
   implemented, because the byte order it stores is decided in
   lib/hash.c, which is not in this repository. Nothing was computed.
@ENDFRAG

@NOTE That is the house style in one paragraph: the command does not
half-implement somebody else's interface, it does not guess at a byte
order it cannot check, and it tells you exactly why rather than saying
"bad arguments". A guessed-at compatibility is worse than none.

**A stopped hash prints nothing.** Press a key during a long digest and
you get:

@FRAG
   stopped part way, so NO DIGEST IS PRINTED. A hash of part of a
   range looks exactly like a hash of all of it and is not one.
@ENDFRAG

@SECTION Files on the boot medium

@FRAG
ls [path]                    also fatls
load <path> [address]        also mount, fatload, f
save <path> <address> [length]
cat <path>
mkdir <path>
rm <path>                    also del
rmdir <path>
rename <old path> <new path> also mv
@ENDFRAG

**A path names its partition.** Put the partition number and a colon in
front: `2:/exfat test/random-1MiB.bin` is on partition 2, and
`2:hello.txt` is the same as `2:/hello.txt`. A path with no prefix is
**always partition 1**, the boot partition - never "whichever partition
was used last" - so `save KERNEL8.IMG ...` cannot be redirected onto a
data partition by an `ls 2:/` typed earlier. Quote a path that contains
spaces. `f` on its own lists every partition in the table, what it is,
and its cluster size.

**A data location that the medium decides.** Recipes and tools do not
write `2:/` or a bare partition-1 name for data such as weights and model
packs. They write `data:/models/MODEL.PMW`, which means
`<data.path>/models/MODEL.PMW`, where `data.path` is an ordinary setting:

@FRAG
settings set data.path 2:/
settings save
load data:/models/MODEL.PMW 40000000
@ENDFRAG

**One partition: leave `data.path` unset**, and `data:/` is the root of
partition 1. **Two partitions: set it to `2:/` once** and save it. `settings`
says where `data:/` points, or that it is unset. `load`, `save`, `ls`, `cat`,
`mkdir`, `rm` and `rename` all take the form. A `data.path` that itself starts
`data:` is refused, and so is a joined path longer than 1023 bytes.

@NOTE `data:` is in the source from commit `c5e70f8`, which comes after build
165. A board running 165 or earlier refuses a `data:` path (it reads it as
a folder on FAT partition 1: volume error 3). The
bench stick's weights still sit on partition 1 until they are moved.

**FAT32 and exFAT partitions take the same paths**: folders at any depth
and long UTF-8 names, matched without regard to case. On FAT32 a file with a
long name can also be reached by its short alias (`B84DET~1.IMG`), and a
name Anvil creates that does not fit 8.3 gets one, generated the way Windows
does. Until build 168 a FAT32 partition was read at its root only, by 8.3
short name.

`mkdir` makes one directory (its parent must exist), `rm` removes one
file or one EMPTY directory and never anything recursive, `rmdir` removes
one EMPTY directory and refuses a file, and `rename` renames or moves an
entry within one partition - including a rename that only changes the case
of a name. Each is write-gated the same way `save` is: the block writer is
armed for the one change, the volume is marked dirty before anything is
written, the stick is asked to commit its cache, the volume is marked clean,
and the writer is disarmed again. A file or folder created or written gets
the wall-clock time when the clock holds a trusted time (set by hand or by
SNTP), and 1980-01-01 00:00 when it does not.

From a recorded board session on build 164, with a USB stick whose
partition 1 is the FAT32 boot partition and partition 2 an exFAT data
partition:

@FRAG
pmf> f

On build 165 and earlier the stick read at about 3 MB a second whichever
filesystem was asked - the 324 MB weights file loaded from partition 2 in
105.6 s and the same bytes from partition 1 in 103.7 s - and a 16 MiB `save`
to exFAT took 172 s. Neither was the filesystem's format. The USB driver
moved one 512-byte block per device command, three round trips per block
(forum 895); the exFAT writer read every sector before writing it and zeroed
every new cluster first (forum 893); the FAT32 writer wrote four FAT sectors
per cluster (forum 896); and an exFAT mount read one sector per byte of its
up-case table, so every switch between partitions cost about two seconds
(forum 897).

@NOTE The storage speed change of 2026-09-17 moves up to 1 MiB per READ (10)
or WRITE (10), lets the stick send its data in bursts, hands every run of
whole sectors to the stick in one call, keeps FAT and allocation-bitmap
changes in memory until a sector of them is complete, and no longer reads or
zeroes a file cluster before writing it. The order in which a change reaches
the stick - allocation, then data, then the directory entry, with the volume
marked dirty first and clean last - is unchanged. The speeds a board shows
with it have not been measured yet; this page gives them once they are.
`usb read <block> <address> <count>` moves 2048 blocks per call, so it times
the transport without a filesystem in the way.

A refusal names the layer that refused and says what to check, and the
reason it gives is the one the layer had AT THE MOMENT IT REFUSED. That
distinction is not pedantic: a change that fails is followed at once by a
flush, to leave the medium consistent, and a flush that succeeds leaves
the filesystem reporting no error at all - so a reason read afterwards is
about the flush. Until build 180 a refused `mkdir` could therefore print
*The medium said: nothing went wrong*, which sent a reader looking in the
wrong place. It now prints what the filesystem said when it said no.

@TRAP A layer that refuses and names nothing is not a success. If you ever
see *file error 9: the filesystem refused and named no reason*, the fault
is in this monitor and not in the medium - the operation did not happen,
the medium is untouched by it, and the thing to report is the command you
typed. It is a separate sentence precisely so that it can never be read as
an ordinary outcome.

A board
running build 167 or earlier still answers `ls OVERLAYS` with *volume error
3: that partition is FAT, and FAT is read here at the root directory only*;
from build 168 it lists the folder.

@SECTION What `usb tree` says about the link under the stick

`usb tree` lists the host controller, its root ports and what is plugged
into them. From build 174 it also prints the link the controller itself is
on, which is the first thing to look at when the storage is slower than the
medium should be.

The controller line reads `controller link   PCI Express 5.0 GT/s x1,
spread-spectrum clocking on, controller firmware 000138C0` - the trained
speed and lane count as the root complex reports them, whether
spread-spectrum clocking was entered, and the controller's own firmware
version. A speed the driver does not have a name for is printed as
`speed code <n>` rather than guessed at. On a board with no such link every
part of the line is absent rather than invented.

Each connected port then carries `link state U<n>` and `U1/U2 timeouts
<a>/<b>` after its speed: the port's current link state (`U0` is active) and
the two low-power entry timeouts the controller is holding.

@NOTE Nothing here changes throughput on its own. Spread-spectrum clocking
is an electromagnetic-emissions measure, not a speed control, and both
Linux and U-Boot enable it on this controller straight after the link comes
up. It is printed because it was never enabled at all until build 174, and
because a link that trained at 2.5 GT/s instead of 5.0 GT/s, or at the wrong
width, would cap every transfer on the bus - and until this readout existed
there was no way to tell from the board which had happened. The values a
real board shows are added here from the first session that runs it.

@SECTION `usb link` - the same link in raw registers

`usb tree`'s controller line ends with the words `spread-spectrum clocking
on`. Those words come from a single flag, and a flag is the one kind of
answer nobody can check: it reads exactly the same whether the driver turned
spread spectrum on, found it already on, or only believes it did. `usb link`
prints the registers underneath instead.

@FRAG
pmf> usb link
@ENDFRAG

Each row is a register: the name the board gives it, its raw value in hex,
every named field inside it with its bit position, and a sentence saying
what the drivers that run this part in service leave there. Ten registers
are shown - the two spread-spectrum registers on the controller's internal
serial bus to its physical layer, the link capability, control and status
words, the controller's miscellaneous control and hardware-debug registers,
the root capability register, the revision, and the link status word.

Three things are worth knowing before reading the output.

A register nothing answered prints `not read`, never `0`. A zero
that means "no bits set" and a zero that means "nobody replied" are
different facts, and printing them alike is how a driver gets credited with
a bit it never read.

The two serial-bus registers are the values captured at the moment
the bring-up sequence read them, not a fresh read. Reaching them means
driving a transaction on that bus, which is a change to the link in order to
observe the link; the other eight are read live when the command runs.

The field values are the architected codes, not their meanings. A
current link speed of `2` is 5.0 GT/s and a negotiated width of `1` is one
lane; turning a code into words is what `usb tree` is for.

@NOTE This command touches nothing. It writes no register, starts nothing
and resets nothing, so it is safe at any prompt and while anything else is
running. A board whose USB host does not sit behind a link of this kind
answers with a sentence saying so, which is a property of that board and not
a failure.

@SECTION `measure` - the board times its own commands

@FRAG
pmf> measure usb read 800 40000000 4000
pmf> measure load "2:/big file.bin" 40000000
@ENDFRAG

`measure` runs the rest of the line exactly as if the word were not
there, leaves the command's own output untouched, and then prints what it
cost on the board's own tick source, in milliseconds and in microseconds.

@NOTE Why this is not a convenience. Every speed this monitor had ever
been credited with was measured by a HOST waiting on the network console,
and that wait includes the console's round trip - which is neither small
nor constant between client programs. One client on this bench measures a
floor of about four hundred milliseconds per command; another measures
about one. The same three-hundred-megabyte load therefore reads as
0.078 s or as 0.502 s depending on which program held the stopwatch, and
the second one looks exactly like a six-fold regression that is not
there. With `measure`, the host clock becomes a sanity check instead of
the measurement.

@TRAP The word is `measure` and not `time`. `time` is already the wall
clock - it sets and shows the date - and taking that word for a stopwatch
would have broken the clock on every board at once for the sake of a
nicer name.

A bare `measure` with nothing after it runs nothing and says so, and
`measure measure <something>` is refused rather than quietly flattened
into one measurement of the inner command.

@SECTION `usb devices` - every device, as it describes itself

`usb tree` answers "what is plugged in". `usb devices` answers "what does
it actually say about itself", which is the question somebody writing a
driver has. Every device, in address order, with:

@FRAG
  its address, slot, port path (3, or 1.4 behind a hub), speed and parent
  idVendor:idProduct, bcdDevice, bcdUSB
  bDeviceClass/SubClass/Protocol with the class in words
  bMaxPacketSize0 and how many configurations it has
  the manufacturer, product and serial-number strings
  the active configuration: value, self or bus powered, remote wakeup,
      bMaxPower in mA, and how many descriptor bytes it published
  every interface and alternate setting, in words, with which driver
      has claimed it - or "no driver"
  every endpoint: address and direction, type, wMaxPacketSize,
      bInterval, and the SuperSpeed companion's bMaxBurst where there
      is one
@ENDFRAG

`usb devices <n>` prints one device and then its raw descriptor bytes -
the device descriptor and the configuration descriptor with everything
nested under it - as a hex dump. That is what is needed when the decoded
view is not enough: a vendor descriptor this monitor does not name, a
field somewhere the specification does not put it, a device lying about
its own lengths.

@NOTE A string row never prints blank. A device that HAS no serial number
says `none` and a device that has one and would not hand it over says
`not read`, because those are different facts and a blank line for both
is how a reader concludes the first when the truth is the second.

@TRAP The walk over a configuration descriptor refuses rather than
guessing. A record that reports a length of zero would send a naive walk
round forever; a record that claims to run past what the device actually
sent would walk off the end of the buffer and print whatever is behind it
as an endpoint. Both stop the listing with a sentence saying where. A
malformed descriptor is not an exotic case - it is what somebody bringing
up a new device is most likely to be holding.

The decoding lives in `Anvil/Bus/usb_core.pbi` and knows nothing about
any host controller, so it is the same code on every board Anvil is built
for. A board supplies two procedures that carry a control transfer, and
nothing else.

@SECTION Where the USB stack spends its time: `usb timing`

`usb tree` says what is plugged in. `usb timing` says what the waiting
cost. It prints one row for every place the USB stack waits - not one row
per event - with how many times it waited there, the total, the worst
single visit, and when the site was first reached and last left.

@FRAG
pmf> usb timing
pmf> usb timing reset
@ENDFRAG

Every figure is counted on the board's own 54 MHz architectural counter by
the driver that does the waiting. Nothing about the console is in it. That
matters more than it sounds: every storage figure this monitor quoted
before build 195 was timed by a host waiting on the network console, and a
console exchange has a floor of about four hundred milliseconds - so a
one-block read and a one-megabyte read measured the same, and the
difference between them was noise.

`usb timing reset` zeroes every row. The pattern that answers "what does
this one command cost" is: reset, run the command, read the table.

@NOTE Rows, not a timeline, and that is deliberate. The boot trail is a
timeline and its ring holds 64 entries, while a boot writes about 161 - so
the thirteen seconds worth reading are overwritten by the four hundred
milliseconds that follow them, and the record of a slow boot is destroyed
by the end of that same boot. A fixed row per wait site cannot wrap.
A count beside a total also says more than a timeline does: 800 ms of port
reset is either one slow port or four fast retries, and those are two
different faults with two different cures.

@SECTION What `usb storage` says about the stick

`usb storage` names the device, its capacity, and then three things about
what it is being driven AS. The lines a real board prints are added here
from the first session that runs it; nothing is shown that has not been on
a board.

`transport` is the interface protocol actually in use - `50` is Bulk-Only
Transport - and the length of the configuration descriptor the device
published. If the device ALSO advertises USB Attached SCSI, the command
says so in full sentences, because a stick that offers UAS and is being
driven Bulk-Only is not being asked for everything it can do: UAS queues
several commands at once where Bulk-Only pays a round trip per command.
Anvil has no UAS transport, so it says which one it is using rather than
leaving the reader to infer it.

`burst` is `bMaxBurst` out of each bulk endpoint's SuperSpeed Endpoint
Companion descriptor, AS CONFIGURED - which is not always what the
descriptor asked for. This controller cannot burst a bulk OUT endpoint of
a mass-storage device that sits behind a hub, so such a device is
configured with a burst of 0 and the printed value is the 0, not the 15
the descriptor offered.

@TRAP Until build 195 this driver asked for only the first 64 bytes of a
device's configuration descriptor and then refused, silently and with no
error set, anything whose descriptor was longer. The commonest reason for
a longer one is a second alternate setting - which is exactly what a USB 3
stick that also speaks UAS has. Such a stick was reported as "not mass
storage" and nothing said why. The descriptor is now read in two steps,
the length field is obeyed, and a descriptor that still will not fit is
refused by name.

@SECTION save

@FRAG
pmf> save KERNEL8.IMG 400000 18CE24
@ENDFRAG

Name, address, length - the last two in hex. The length is bytes. Leave
the length out and the file keeps the size it already has; give one and
the file is **resized** to match.

What you will see, from a recorded board session:

@FRAG
The file KERNEL8.IMG on the boot medium is 1809100 bytes long at the moment.
It is being resized from 1809100 bytes to 1625636 bytes to match what
you asked to write.
Writing 1625636 bytes out of memory, starting at 00400000. This
takes a moment and must not be interrupted.
written.
  Saved KERNEL8.IMG on the boot medium.
  That file now holds what was in memory, and the
  block writer has been disarmed again so nothing else in this monitor
  can reach the medium. Saving does not change the boot-file selection;
  reset still loads the configured boot image, not an arbitrary saved file.
@ENDFRAG

@NOTE `written.` is a protocol string too - the update tool checks for
exactly that word. And notice the last sentence about the block writer:
the medium is not writable at rest. `save` arms the writer, writes, and
disarms it again, so nothing else in the monitor can reach the medium by
accident.

@TRAP The failure to memorise:

@FRAG
!! the write did not finish. THE FILE MAY NOW BE PART OLD AND PART NEW.
   Write it again before resetting the board, or it will try to boot
   half of one image and half of another.
@ENDFRAG

If you see that, **do not reset**. Chapter 8 is entirely about that
moment.

@SECTION Getting an image in over the network

@FRAG
net recv <port> <address> [max-length]
@ENDFRAG

Port decimal, address and length hex. It opens a TCP listener for
exactly one connection, then closes it.

@FRAG
pmf> net recv 5001 400000
Listening on port 5001 on every usable addressed interface for ONE connection:
    wired at 192.168.137.2
  Everything it sends goes to 00400000 and the last byte it may
  write is 07EFFFFF, which is 128974848 bytes.
  Send the file and close the connection; the length and the SHA-256 of
  what actually landed are printed here when you do. Any key stops it.
@ENDFRAG

And when the host has sent it:

@FRAG
  Received 1625636 bytes from 192.168.1.24 to 00400000 in 7676 ms.
      That is 206 KB/s.
      sha256 85370e48df79c7fe06956c2c47a27fef049b3e475d44cbba6395422df6ab463f
      The digest is of THE MEMORY, taken after the transfer, and it took 32578
      ms. Compare it with sha256sum of the file on the host: equal means
      the bytes in this board's DRAM are the bytes in that file.
      Nothing has been booted and nothing has been written to the medium.
      boot mem 00400000 enters it if it is a container; save <name>
      00400000 0018CE24 writes it to the boot medium.
@ENDFRAG

@NOTE A close is how the end of a file is announced. A host that stops
sending without closing looks exactly like a host that has crashed, and
the board cannot tell them apart - so a silent peer is reported as an
**incomplete** transfer and what is in memory is part of an image.
Nothing may be booted from it.

@SECTION run, go, and boot

@FRAG
run [address]        also go, g - enter a raw image
boot mem <address>   enter a PMFBOOT container already in memory
boot <name>          read a container off the medium and enter it
boot status          what is armed, and the loop-guard counter
boot ok              clear the loop-guard counter
boot clear           stop booting a file automatically
@ENDFRAG

The difference is the container. `run` jumps at an address and trusts
you. `boot mem` reads the 96-byte header there, checks it, places the
image **at the address the payload was built for**, verifies its
SHA-256, and only then enters it.

What you will see when a payload is entered:

@FRAG
Starting the payload at 00500000. Control leaves the monitor now, and
anything printed below this line came from the payload, not from Anvil.
@ENDFRAG

and when it comes back:

@FRAG
The payload returned to the monitor. Its x0 register held 000000000000000A,
which is whatever it chose to return. A stock image never returns at
all, so seeing this line means the payload was built to come back.
@ENDFRAG

Sixteen hex digits, because x0 is a 64-bit register and always was.

@TRAP `boot mem` places the image **where the container says**, not where
you put the container. For a monitor image that address is `00200000` -
on top of the running monitor. Entering a monitor image with `boot mem`
takes the board down with no console. Chapter 3 says this too; it is
worth saying twice.

@SECTION The deadman

@FRAG
deadman <seconds>    1 to 15, decimal
deadman off          also deadman 0
@ENDFRAG

It is a one-shot hardware watchdog, armed by the monitor immediately
before it enters a payload and stopped immediately after the payload
returns. **It is never running at the prompt.**

@FRAG
The deadman watchdog is armed for 15 seconds. If the payload hangs and
never comes back, the board will reset itself rather than sit there.
@ENDFRAG

@FRAG
The payload came back, so the deadman watchdog has been stopped. The
board will not reset itself.
@ENDFRAG

@TRAP The ceiling is about sixteen seconds and the reported value is the
**floor**, never the request. Ask for `deadman 30` and it is accepted,
clamped, and reported as 15 - because a deadman that fires earlier than
it said it would is worse than none at all.

@NOTE Anvil never pets the deadman for the payload. The payload pets it
in its own loop, and that is the whole reason the deadman makes a
wedged board impossible: a monitor that petted a watchdog on behalf of a
program it is not running has disarmed the one thing standing between a
hung payload and somebody driving to the bench.

@SECTION What happened to the last payload

@FRAG
last run
@ENDFRAG

@TRAP This command is in **monitor build 152**, which is built and not yet
flashed. Build 151 and older answer it as an unknown word.

The monitor writes down what became of every payload it enters: at the
jump, at the return and at a processor exception, in the boot phase record's
page, which a reset does not erase. `last run` prints that record - one
machine line for tools, then the same facts as sentences:

@FRAG
LASTRUN <run> <state> <restarted> <deadman> <x0> <address> <ms> <esr> <pc> <far>
@ENDFRAG

`state` is 0 nothing recorded, 1 entered and not back, 2 returned, 3 stopped
at a processor exception. `restarted` is 1 when the board has booted since
the payload was entered - the record counts boots - which is how "the
deadman reset the board" is something the board says rather than something
a host guesses. The run number rises at every jump and at nothing else, so a
refused `boot mem` leaves it where it was.

@NOTE It exists because a return line can be lost on the network while the
payload came back perfectly well. Chapter 6 has the measurement, and the
host runner asks this command whenever a return line does not arrive.

@NOTE The deadman is **one-shot**, as it says: the setting is taken at the
jump, so the payload it was armed for spends it and the next payload runs
without one unless `deadman` is typed again. A refused jump leaves it armed.
Until build 160 the watchdog was stopped after a return but the setting
stayed armed for every later payload (forum 879).

@SECTION The boot trail

@FRAG
trail
@ENDFRAG

In the shipped image since build 165. Every step of the configuration half of the boot - the PCI
Express and USB host phases, every wait for a USB event and whether it ran
out, every SCSI command sent to the USB stick with the status and sense that
came back, every block read, and each step of mounting the filesystem - is
written with its millisecond into a ring of the last 64 in the boot phase
record's page, which a reset does not erase. The ring the previous boot left
is kept beside this boot's, and `trail` prints both: `TRAIL 1` lines are the
previous boot, the last one being where it got to.

A 15-second watchdog, petted by every one of those steps, covers the
configuration half only. A boot that has stopped is reset once, and the boot
after it prints `!! THE PREVIOUS BOOT STOPPED` with its last six steps on
the screen and the serial line before USB starts. The watchdog is never armed
on the boot straight after a stopped one, so it can cost one extra reset and
never a board that resets for ever.

A boot that is merely slow is not reset. Every USB wait lasts five seconds
at most and records a step as it starts, and every SCSI command and every
retry of a stick that is not ready records one, so the longest stretch with
no step on a working board is about five seconds against the watchdog's 15.
The hardware cannot count past a fraction under 16 seconds, which is why the
bound is 15 and why the steps are what keep it safe.

@NOTE **If a boot fails, send this:** the `!! THE PREVIOUS BOOT STOPPED`
line and the steps under it (a photo of the screen is fine), the output of
`trail` from the boot that did reach the prompt, `version`, and what is
plugged into the USB ports. That is enough to say which step a boot
stopped in, which is where a fix starts (forum 880). A power cut clears
the record, so type `trail` before switching off.

@SECTION Settings that survive a power cycle

@FRAG
settings                 list everything, passwords hidden
settings set <name> <value>     the value is the rest of the line
settings remove <name>
settings reveal <name>   print one in full, hidden or not
settings save            write SETTINGS.TXT to the boot medium
settings load            read it back
settings discard         accept a part-read file so a save is allowed
@ENDFRAG

Nothing loads the settings file for you after a reset; `settings load`
does it, and bringing the medium up is slow and noisy, which is why it
is not done unasked.

@NOTE Anything whose name contains `password`, `passphrase` or `secret`
is masked in the listing, because that output also goes to the on-screen
console and into the next screenshot anybody takes. `settings reveal` is
the deliberate keystroke that puts one on the screen - which is why it
will not do it for a name you did not type.

@TRAP The refusal that saves your configuration file:

@FRAG
!! refusing to save. The last load stopped at a bad line, so the table
   in memory holds only the part of SETTINGS.TXT above it, and a save
   rewrites the whole file from the table - it would delete every line
   after the bad one, silently and permanently.
@ENDFRAG

@SECTION What SETTINGS.TXT looks like on the medium

You do not have to write it by hand - `settings save` writes it - but it
is a text file and you will read it sooner or later:

@FRAG
key=value        one to a line; the FIRST '=' splits, later ones are
                 part of the value
keys             lower case, a-z 0-9 . - _ , at most 31 bytes
values           printable ASCII, at most 95 bytes, and may NOT begin
                 or end with a space
# or ;           a comment line
@ENDFRAG

Keys are case-insensitive on the way in and always written back in lower
case. Blank lines are ignored. A save writes LF endings; a load accepts
LF, CRLF or a lone CR. At most **32 keys and 6144 bytes**, and a UTF-8
byte-order mark is skipped only at the very start of the file.

@TRAP **Your comments are not kept.** A save rewrites the whole file from
the table in memory, so the first `settings save` after you hand-edit the
file deletes everything you wrote in it and replaces it with Anvil's own
banner. This is also why a part-read table refuses to save at all.

An unknown key is **not** an error - it is simply stored - so a
misspelled name becomes a new setting rather than a complaint. The names
with code behind them are the network addresses (`net.address`,
`net.netmask`, `net.gateway`, `net.server`, `net.dns`), the four Wi-Fi
slots (`wifi.N.ssid`, `wifi.N.password.plaintext`), the clock
(`clock.utc`, `clock.zone`, `ntp.server`), the autoboot
(`boot.file`, `boot.delay`, `boot.maxfails`, `boot.fails`), the fan
(`fan.pin`, `fan.mode`, `fan.lowF`, `fan.highF`, `fan.hystF`, `fan.hz`)
and the panel (`screen.rotate`, `screen.scale`, `touch.axes`). The fan
thresholds carry their unit in the name because they are Fahrenheit and
an older Celsius spelling existed; the old names are read once to
migrate and then removed.

@NOTE A commented example of the whole file, safe to copy, is in the
repository at `Boards/RaspberryPi4/sdcard/SETTINGS.TXT.example`, beside
the boot-volume skeleton chapter 3 points at.

@TRAP **A passphrase in this file is plain text**, on purpose: the radio
needs the passphrase itself, and hiding it on a medium whose reader also
holds the key would only look like protection. After a successful
handshake Anvil also caches the derived key as `wifi.N.pmk.secret` so the
next boot skips a ten-second derivation - and **that value joins the
network as well as the passphrase does.** Never copy one to another board
or into a file you share.

@SECTION Network and radio

@FRAG
net                   show the four addresses and the wire
net address <a.b.c.d> / netmask / gateway / server / dns
net recv <port> <addr>
net up / net down / net forget
net stats             what each network controller counted
dhcp                  ask for an address now
get <name> [address]         fetch over TFTP
put <name> <address> <len>   send over TFTP
ping <host> / dns <hostname>
http serve [port]     default 8080, / and /health only
@ENDFRAG

@FRAG
wifi                  list stored networks, passphrases hidden
wifi ssid <slot> <name>      the name is the rest of the line
wifi phrase <slot> <phrase>  the phrase is the rest of the line
wifi scan / join / rejoin / ip / forget <slot>
wifi link [on|off]    the keepalive and auto-reconnect
@ENDFRAG

Four networks can be stored, in slots 1 to 4, and **the number is the
order they are tried in** - slot 1 first.

`dhcp` takes no arguments. What you will see on success:

@FRAG
Lease accepted on wired:
  address   192.168.1.25
  netmask   255.255.255.0
  gateway   192.168.1.2
  server    192.168.1.2
  lease     86400 seconds remaining
The lease is runtime protocol state and is not written over saved static
settings. Renewal, rebinding and expiry continue automatically.
@ENDFRAG

@NOTE That last sentence is a design decision worth noticing. A lease is
not a setting. It is never written over the static addresses you saved
on purpose, and it renews itself without you.

`net stats` (also spelled `net counters`) answers a different question
from `net`. `net` prints this monitor's own tallies - frames in, frames
out, refusals. `net stats` prints what the network HARDWARE counted, for
every interface, whichever one traffic is currently leaving by. It reads
and prints and changes nothing, so it is safe to type twice in a row and
compare.

Under THE WIRED ETHERNET it prints the Ethernet controller's own
statistics since the interface last came up: pause frames sent and
received, good frames received and sent, and then only the error and
overrun counters that are not zero, with the number of bring-ups and
auto-negotiation restarts beside them, because every bring-up clears the
block. The first line always prints:

@FRAG
  Pause frames this board SENT: 0.
@ENDFRAG

That line must read zero. A non-zero number means the board is telling
the machine at the other end of the cable to stop transmitting, and the
command says so in capitals. If the controller has never been started, it
says that instead and reads nothing.

Under THE WI-FI RADIO it says whether the radio holds an address, and that
the radio has none of those counters: the CYW43 keeps its equivalents in
its firmware and this driver does not ask for them. An absent number is
not a zero. For the radio, `net` and `wifi status` are the readings.

@SECTION Who the network console belongs to

The network console answers one host at a time. The first datagram that
arrives while nobody owns it makes that host the owner, and every other
host is answered `BUSY` while the owner's command runs. When the command
finishes, the console is nobody's again.

A host that stops talking cannot keep it:

@FRAG
an empty datagram           never takes the console, and is not answered
an owner at the prompt      loses it the moment another host sends, if
  with nothing typed        nothing it sent is still waiting
an owner at the prompt      loses it after 60 seconds of silence; the
  with a half-typed line    half line is erased, never run
an owner whose command      keeps it, however long the command is silent
  is running
@ENDFRAG

So a host tool that finishes and exits hands the console on to the next
host at once. An empty datagram is how a host keeps its own flow alive
through a firewall during a long command; it neither claims nor refuses
anything. See forum topic 888.

@SECTION reset

@FRAG
pmf> reset
Resetting the board now. The firmware reloads this monitor from the boot
medium and it starts again in a few seconds. Nothing in memory survives.
@ENDFRAG

No confirmation prompt. `reboot` and `r` are the same command.

@SECTION The board itself

@FRAG
info               what board this is, its memory, clocks    also board, i
uptime             also up
clock [rate]       rate in DECIMAL
cache              turn the caches on or off, and report
gpio ...           pins in DECIMAL
i2c probe / read / write / speed
usb info / tree / storage / read
mmc info / read / write
fan ...            the PWM fan and the part's temperature
mod ...            driver modules - chapter 9
screen ... / screenshot / shot ...
el3test            one bounded secure-timer interrupt, then one BRK
coretest run|stop|status     chapter 7
@ENDFRAG

@TRAP Number bases are not uniform and there is a reason for each. Memory
addresses, lengths and CRCs are **hex**, because that is what an address
is. GPIO pin numbers, clock rates, `deadman` seconds, `sleep` seconds
and `net recv` port numbers are **decimal**, because that is how those
things are written on a schematic, in a datasheet and in a socket. When
in doubt, `help` states the base for each command.

@NOTE `el3test` and `coretest` are explicit diagnostics and are never
boot actions. There is no automatic start and no payload form of either.
After `coretest run`, restart before changing cache policy or entering a
payload - chapter 7 explains exactly why.

@SECTION info, and how much memory this board has

`info` is the board's own account of itself. It prints what the monitor
knows without asking anybody - what it refuses and why, and which
exception level it came up at - and then what the firmware says: the
board, its revision code, **how much memory is fitted**, the
temperature, the clock rates and the I2C bus.

The memory row is decoded from the board revision code the firmware
reports, which carries the size in a field of its own. That is a
different question from the mailbox tag called "get ARM memory", which
answers with the ARM's share of the first gigabyte - about 948 MB on a
4 GB board - and as a memory size would be wrong by a factor of four.

@FRAG
board       Pi 4 Model B, BCM2711, 4 GB, rev 1.1   (revision code $00C03111)
RAM         4 GB, from the board revision code the firmware reports.
            An address past it is refused, naming that size. Memory
            runs from zero, stops at the peripheral aperture and
            resumes above four gigabytes; both runs are inside the
            one figure above.
@ENDFRAG

@NOTE Those lines are copied from the monitor's **source**, not from a
recorded board session: the RAM row is new and no board has printed it
yet. The `board` row above it is the line `info` has always printed. An
image built before this change prints that row and goes straight on to
the temperature.

**Why the monitor cares.** A Raspberry Pi 4 is sold with 1, 2, 4 or 8 GB
fitted, and Anvil is the same image on all of them. Until it could size
itself, `memory 80000000` on a 1 GB board read an address with no memory
behind it, got back whatever the bus left on the wire, and printed it
under a heading that says it is the contents of memory. On that board it
is now refused, in the same shape every other address refusal takes:

@FRAG
pmf> memory 80000000 40
!! memory was refused: 80000000 .. 8000003F
   is above the 1 GB of RAM this board has.
   That space runs 40000000 to FBFFFFFF.
   Nothing was dumped. THIS REFUSAL IS KNOWLEDGE, NOT IGNORANCE:
   the board asked how much memory is fitted and this address is
   past it. Reading it would not stop the board - it would answer
   with whatever the bus left on the wire, which is the worse
   outcome: a plausible value under a heading that says memory is
   indistinguishable from the truth, and a stop at least announces
   itself. info says what the size is and where it came from.
   If you have a reason to touch it anyway, type
       force 80000000
   and then repeat the command on the very next line. That arms this
   one address for one command and nothing else. Typing the address
   twice is the confirmation - there is no flag, because a flag is
   something a script can carry without anybody having decided.
   info lists what this board does know, and where each answer came
   from.
@ENDFRAG

The same refusal stands in front of `load`, `save`, `fill`, `copy`,
`compare`, `crc32`, `sha256sum`, `mtest`, `readback`, `net recv` and
`boot mem` - every command that takes an address from you - and each one
names its own verb on the "Nothing was" line.

@TRAP **Memory is in two runs on this board, and you can only reach the
first one.** It starts at zero, STOPS at `FC000000` where the peripherals
are, and resumes at `100000000` - so a 4 GB board's last 64 MB lives
above four gigabytes. **This monitor does not map any of that.** Its page
tables cover the low four gigabytes and the PCI Express window and
nothing in between, so an address like `103FFFFC0` is a translation
fault, and a fault here is not a refusal: Anvil prints one fatal line and
stops, the console dies with it, and the board has to have its power
removed. That is measured, not theorised - it is how this paragraph came
to be rewritten. Every address above four gigabytes except the PCI
Express window is therefore refused, and the refusal says the tables
rather than the size. A 1 GB or 2 GB board has no second run at all. The
one size `info` prints is the memory FITTED, which is why it is a size
and not a top address.

Nothing is refused on a board that cannot say what size it is. If the
mailbox is down, or the firmware returns an old-style revision code with
no memory field in it, the RAM row says which and the guard stands down
rather than guessing - the same behaviour every image had before this
change.

**The size reaches the hardware too.** The PCI Express controller's
inbound DMA window - the aperture the USB host controller reads your
memory through - is programmed to the smallest power of two that covers
the memory fitted, which is what Linux and U-Boot do: 1 GB gets size
code 15, 2 GB gets 16, and 4 GB and 8 GB both get 17, because the
wrapper erratum stops inbound transfers at 3 GB and a larger window
would describe address space nothing can use. You never type anything
for this. The one time it says something is when the size is unknown:

@FRAG
!! this board could not say how much memory it has, so the PCI Express
   inbound window is programmed at its largest useful size instead of
   being fitted to the memory. That is the safe direction - a window
   bigger than the memory behind it costs nothing - and transfers are
   still refused above the 3 GB the wrapper erratum allows. Type info
   to see why the size is unknown.
@ENDFRAG

It is printed once per boot, the first time anything brings the USB
controller up, and it is a note rather than a failure: the window is
then exactly what every image before this change programmed.

@SECTION There is no loop command, on purpose

`help` says it in one line:

@FRAG
  loop is deliberately absent - it cannot return at all.
@ENDFRAG

That is the console's whole philosophy in a sentence. A command that can
take the prompt away from you and never give it back is not a
convenience.
