@CHAPTER What Anvil is
@INTRO A monitor that stays resident while your program runs, owns the machine's physical services, and lends them back through a versioned table.

@SECTION The one-sentence version

Anvil is a bare-metal mini-kernel, bootloader and recovery monitor. It
boots a board with no operating system underneath it, gives you a
prompt, and can load and run your program while remaining in memory the
whole time.

It is MIT licensed, and the source is the whole of it - no vendor
toolchain, no runtime library, no second hardware stack hiding
underneath.

@SECTION What "resident" means, and why it is the whole design

The usual arrangement for a bare-metal program is that it owns
everything. It brings up its own clocks, its own serial port, its own
storage, its own network. Two such programs on one board have two copies
of every driver, and neither can help you when the other one hangs.

Anvil is the other arrangement. It **stays in memory while your program
runs.** It owns storage, interrupt control, clocks, console paths,
network links, display, DMA and watchdogs, and it exposes them through a
versioned table of function pointers instead of making every program
bring a second copy of the hardware.

Your program - a **payload** - can therefore be pure computation, or
computation plus a few service calls, and it does not have to know how
any of the peripherals work.

@NOTE The practical consequence is the one you will feel first. When
your payload finishes, there is still a monitor there to tell you what
happened, take a screenshot of the frame you left behind, and let you
type the next command. When it hangs, there is still a watchdog to reset
the board and a prompt waiting afterwards. You do not have to power
cycle to iterate.

@SECTION The three things Anvil is, at once

**A monitor.** It gives you a prompt on a serial line and over the
network: read and write memory, hash a region, list and load files, look
at the memory map, drive GPIO and I2C, take a picture of the screen.
Chapter 4 is the command set.

**A bootloader.** It can load a program from the boot medium or from
memory, verify it against its own digest, place it where it was built to
run, and enter it - automatically at power-up if you ask it to, with a
loop guard so a payload that keeps hanging cannot take the prompt away
from you.

**A mini-kernel.** It publishes services to a running payload through a
table, and it takes the machine back afterwards - restoring the devices
the payload did not claim, including rebuilding a network controller
without losing its addresses or its unexpired lease.

@SECTION The shape of the source

One portable core, one hardware composition per target:

@FRAG
Anvil/Core/*.pbi        the portable monitor: command loop, parsing,
                        settings, transfer and boot logic, hashes,
                        network orchestration
Anvil/Hal/*.pbi         the hardware contract and the versioned ABIs
Anvil/Kernel/*.pbi      AArch64 architecture, not any chip: the
                        exception vectors and the scheduler's contexts
Anvil/Storage/*.pbi     FAT32, exFAT, the one path layer over them,
                        the file seam any block-device board answers
                        with, and the A/B boot-control record
Anvil/Graphics/Vulkan/  an experimental Vulkan-compatible foundation
RaspberryPi4/Board/     the BCM2711 memory map, boot order, console,
                        storage, display, board policy
RaspberryPi4/Lib/       the BCM2711 drivers
ArduinoQ/, RaspberryPi3/, RockPi4C/    the other targets, the same way
@ENDFRAG

The core calls portable names. A board owns the choice of hardware and
the implementation behind those names. Shared code uses `.pbi`, which
carries no target identity; Pi 4 hardware code uses `.pi4`, and the
other boards their own extensions.

A LIBRARY EXISTS ONCE. Boards differ in the interface under it, not in
a second copy of it. If a file has no chip in it, it belongs in a shared
folder with a `.pbi` name, and every board includes the same one.

Every one of those interfaces is declared in `Anvil/Hal/hal.pbi`,
including the two that were real and undeclared until 2026-09-18: the
console bytes a board prints and reads through, and the monotonic clock
it counts in. A board that wants a prompt implements the first; a board
that wants a timestamp implements the second; neither invents a name.

@NOTE The extension is not a label, it is enforced. Including a `.pi4`
file from a `-t pi3` build is refused by the compiler, by name, at the
first cross-chip include: "If it is really for the BCM2837 (Raspberry Pi
3 Model B): include that chip's own libraries instead." That refusal is
right - it stops a board collapsing into dozens of undeclared-register
errors inside a library nobody meant to include. It also means a file
that is perfectly portable is UNREACHABLE from another board while it
carries a board's extension. Architecture-neutral code therefore has to
be moved and renamed to be shared at all; leaving it where it is
guarantees the second board writes its own.

@NOTE Target-specific names deliberately do not leak into the portable
contract. That is not tidiness - it is what makes a new board a matter
of writing one composition rather than forking a monitor.

@SECTION What runs where

AArch64 processors have privilege levels numbered EL0 to EL3, with EL3
the most privileged. What matters to you is a short list.

**The firmware runs first**, before anything in this repository. It
reads `config.txt`, sets up clocks and power domains, and loads
`kernel8.img` to the address it was told to.

**Without the firmware stub**, the firmware drops the image to **EL2**
and Anvil runs there. That is the default arrangement.

**With the firmware stub installed**, a 512-byte piece of AArch64 called
`armstub8.bin` runs first at EL3. It does the machine setup the stock
stub does - the timer, the interrupt controller, parking the other three
cores in the spin table - and then **deliberately omits the exception
return to EL2**, branching into `kernel8.img` with the processor still
at EL3. Anvil then runs at EL3.

**A payload is entered at the same level Anvil is running at.** Anvil
does not change the level to enter you and you must not change it
either.

@TRAP **Never hard-code the exception level in a payload.** This is not
advice; it is a bug that has already happened. A large payload's
precondition asserted "we must be at EL2", and the day the monitor
started booting through the stub at EL3, that payload refused to run -
correctly, having computed nothing, which is why one run found it. The
refusal was right and the check was wrong. Ask the service table.

@NOTE The EL3 stub is optional, is never built by a plain build, is
never installed by a build, and the EL3-to-EL1 handoff is **still
incomplete**. Do not change boot configuration without physical access
to the board. Chapter 3 has the full procedure and the reason each step
is separate.

@SECTION What a payload is

A compiled image with two properties: it was built to **return**, and -
if it wants services - it declared that it wants the service table.

Anvil places it at the address it was linked for, verifies its SHA-256
**at that address**, zeroes its BSS, switches to its stack, masks
interrupts, and branches into it with the service table's address in
`x0`. When it returns, Anvil prints all sixteen hex digits of `x0`.

@FRAG
Starting the payload at 00500000. Control leaves the monitor now, and
anything printed below this line came from the payload, not from Anvil.
@ENDFRAG

@FRAG
The payload returned to the monitor. Its x0 register held 000000000000000A,
which is whatever it chose to return. A stock image never returns at
all, so seeing this line means the payload was built to come back.
@ENDFRAG

The contract that goes with it is short. The payload may use its
declared image, BSS and stack, the processor state it was handed, and
devices it explicitly claims. It must preserve Anvil's image and BSS and
must not reconfigure unrelated devices. Chapter 5 is that contract in
full.

@NOTE The service table is **call-and-return only**. Anvil never calls
back into a payload: no callbacks, no handlers, no "register a function
and I will call it". Where a service looks like it wants a callback it
provides a **queue** instead - which is why touch and vehicle input are
polls. The reason is that Anvil's drivers keep their state in globals
with one writer and no lock, and a callback would re-enter them on top
of a call already in progress.

@SECTION What a module is

A payload borrows the machine. A **module** extends the monitor.

A module is a driver in a file - a `.MOD` container on the boot medium,
verified against its own digest, placed in a reserved area, relocated,
matched to a device the board declares, and asked to publish the service
it implements. The point is that a board which does not have a
particular piece of hardware should not be carrying its driver.

@TRAP The published state of that work is **placement infrastructure
only**: the container format and the relocator exist and have executable
tests, and neither board activates the engine. Chapter 9 says exactly
what exists and what does not, because this is the one part of Anvil
where it would be easy to read a feature list and plan around something
that is not there yet.

@SECTION The memory map is measured, not declared

Anvil reads its own image-extent symbols at run time. Its code
reservation is the live image rounded up to a megabyte, and the first
payload window begins at the next boundary above that.

So **the addresses move when the monitor does.** The low payload window
started at `00400000` on one build and `00500000` on the next, for no
reason except that the image grew.

@FRAG
pmf> map
THE MEMORY MAP, AS THIS IMAGE MEASURES IT
  this image      00200000 to 004B144B   2823244 bytes, measured from the image itself
  ...
  stage a file at 00500000               which is what the upload tools ask for

Where a payload may go:
  the low window   00500000 to 07EFFFFF   (about 122 MB)
  the high window  40000000 to FBFFFFFF   (about 3 GB)
  Nothing in this map is a constant this program was told.
@ENDFRAG

@TRAP Every host tool asks the board for that address instead of
carrying one. Four tools used to carry `0x400000` as a constant of their
own - four copies of one number on the far side of a cable, none of
which could find out it had changed. **Do not copy an address out of a
note, an example, or this book.** Type `map`.

The monitor also refuses writes into the regions it owns - its code, its
variables, the autoboot record, the framebuffer, the secondary-core
stacks, the module arena, the boot phase record, the screenshot area -
so `write`, `fill` and `copy` cannot reach them by accident.

`info`.

@SECTION One last thing, about how this project talks

You will notice that the monitor's messages are long. A refusal is a
complete sentence, it keeps the numeric code, it says what the state now
is, and it names the first thing to check.

That is deliberate and it is the project's whole philosophy in one line:
**a loud error beats a silent wrong answer, always.** A program that
refuses is fixable. One that quietly does the wrong thing costs somebody
a week.

You will also notice that the documentation says what has **not** been
proven, in the same breath as what has. Chapter 11 is a map of seventy
notes that mostly exist to mark a boundary. Trust that habit; it is the
most useful thing in the repository.
