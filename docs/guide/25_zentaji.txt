@CHAPTER Anvil on Zentaji

@INTRO Zentaji is a custom emulated computer with its own 64-bit instruction set. Its boot ROM loads Anvil as the selected bootloader and resident monitor. The current production composition reaches a text prompt; the native GPU components are qualified separately and do not yet provide the Neon Arcade desktop.

@SECTION Build and boot

From the Anvil repository root, select the existing multi-target Forge
executable explicitly. The following build command has been run on Windows;
replace the placeholder with your installed executable's path.

@FRAG
python tools/build.py zentaji --compiler <Forge executable>
@ENDFRAG

A successful build publishes `build/zentaji/anvil.zex`, its `.boot.json`
metadata and `.zmap` source map. The metadata records the counted build,
image digest, entry and memory requirements. The source map records the source
hashes. Each successful monitor build advances the build number automatically.
Do not substitute an ARM image: Zentaji executes native Zentaji instructions.

Configure the machine ROM to load this image from its selected host file or
boot disk. The monitor acceptance tool exercises both routes using the
published image. This invocation has been run with the native tools directory
from the compiler repository:

@FRAG
python tools/zentaji_monitor_check.py --zen-tools <tools/zentaji directory>
@ENDFRAG

It reports PASS only after checking the actual ROM boot, monitor version,
commands and memory boundaries against native execution. A host-file profile
without a disk can reach the prompt, but correctly refuses storage operations.
The machine's own ROM console and Anvil's `pmf>` prompt are different stages.

The shared monitor supplies command policy, settings, FAT32/exFAT and the
application service table. The Zentaji hardware layer supplies serial, native
text, keyboard/mouse input, persistent queues, clock and timer ownership.
Idle command and countdown waits use the CPU's WFI instruction and timer wakes.
There is no operating system beneath the guest monitor.

@SECTION Load a native application

The monitor accepts version 2 PMFBOOT containers tagged ISA 2, target 1.
Use `boot APP.PMF` to load from the selected filesystem, or `boot mem`
with an address for a container already in memory. The shared loader checks
metadata, complete source ranges, placement, stack and entry alignment, then
hashes the placed bytes before entering the application. Untagged legacy
containers and containers for another architecture are refused.

Service-backed applications retain Anvil's resident device owners and use
the shared service table. Ordinary supervisor applications receive quiesced
owners and must return their devices quiescent. A return that changes owned
timer, disk or text hardware is refused rather than overwriting a foreign owner.
This boundary is not isolation from malicious supervisor code.

Saved `boot.file` and `boot.delay` use the existing shared countdown and
reboot-loop guard. Persist settings with `saveenv`. Automatic entry records
the attempt before calling the application. A returned application is
acknowledged with `boot ok`; return alone does not erase the guard.

The application checks use an 8 MiB machine profile. The exact monitor floor
in the build metadata includes a staging page, but each application still needs
space for its image and stack. That text-profile size is not a promise that a
future graphics composition fits in the same memory.

@SECTION What graphics currently does

The graphics memory owner reserves a permanent page-aligned arena below the
text reservation and supervisor stack. Payload placement excludes it. The
display owner uses two or three pinned buffers, presents only retired native
GPU work, and waits for the real display latch through timer/WFI. A timeout
does not release memory or claim that presentation finished.

The native Vulkan backend supports color clears, opaque triangle drawing and
attachment LOAD. Pipeline creation lowers verified typed shader IR to native
GPU instructions and retains resource requirements independently of source
shader-module lifetime. Native cases check exact pixels, indexed draws,
scissor/clear behavior, instances, sample-mask zero and independent scanout CRCs.

Public combined-image descriptors use the machine's actual TEX2D boot-ROM
service for nearest and bilinear sampling. BGRA8 images use normalized
clamp-to-edge coordinates and matching minification/magnification filters;
mixed filters are refused. Source images can use linear or the native backend's
private optimal layout. An explicit backend capability controls optimal color
attachments in both the format query and image creation, so a backend that only
samples optimal images does not acquire render-target support implicitly.

Native cases render, transition and sample real GPU images, checking RGBA pixels,
filtered alpha, source immutability, retained resources and scanout CRCs.
Malformed or aliased descriptors are refused before launch.
Native blending supports SRC_ALPHA/ONE_MINUS_SRC_ALPHA for RGB and
ONE/ONE_MINUS_SRC_ALPHA for alpha, both ADD. The older SRC_ALPHA-for-alpha
equation has its own portable mode and capability and is refused on this native
backend. Pipeline creation checks the exact equation; it does not substitute one
because the device supports a different form of blending. Native cases check
full RGBA and display CRCs at alpha zero, quarter, half and one, including a
second scissored attachment-LOAD pass. The shared software executor separately
checks both equations against expected pixels.

Shared Neon textured, line and outline builders request ONE for source alpha;
V3D supports both alpha modes. Native GPU cases execute the production textured
builder and atlas shader with push tint, zero UBO, binding1 sampling, dynamic
state and exact RGBA/display CRCs. V3D packet/list CPU checks leave physical
Pi4 GPU pixel proof owed.

Ordered lists preflight every item before launch. Draws and rectangle clears
reuse one pinned page after each GPU fence, clearing the pass only once. Final
retirement signals the public fence; later faults quarantine all flight
resources until reset.

Owned DMA supplies buffer copy/fill/update, linear transfers and whole optimal
uploads/copies. The CPU writes descriptors; DMA writes pixels. Timer/WFI waits
retire work; failures quarantine resources.

Before Vulkan allocation, DisplayWindow reads native geometry and the descriptor
buffer count, then carves private planes from the graphics reservation. It
refuses a small arena before hardware setup. Writer tokens reject stale reuse
across rotations/restarts; shown or pending planes and a second writer are
unavailable. DMA and the producer GPU fence must retire before presentation.
A pending plane stays unavailable until the real display latch. Submitted or
quarantined writers cannot be aborted or released. The Vulkan bridge pins the
source image/allocation and holds the external GPU lease. Begin requires matching
BGRA geometry, transfer-source usage and GENERAL or TRANSFER_SRC layout. Abort
releases an unsubmitted writer; Commit uses native DMA and waits for the latch
before releasing pins. Uncertain retirement keeps the resources until reset.

Native cases check two GPU colors in private planes, scanout CRCs, unchanged
shown pixels and row/page guards. DMA ownership loss quarantines the writer and
GPU lease. Resident Neon/fonts remain unfinished; the monitor still boots to text.

@SECTION One console model across CPU architectures

The fixed-grid terminal model lives in Anvil/Core/console_grid.pbi. It owns
characters, screen-only styles, cursor, wrap, scroll, viewport and dirty state.
Renderers paint that one model; they do not consume another output stream.
A board supplies proportional-advance measurement when it enables that policy.
The model acquires no display, UART or GPU.

Anvil/Core/console_mirror.pbi holds the bounded screen/style and auxiliary
output taps. Styles remain metadata beside screen bytes, never serial or network
escape sequences. A producer callback drains into the model without painting.
The Pi4 include path remains a compatibility entry for the same shared core.
Optional paint, overlay and drain callbacks retain zero/uninstalled behavior;
concrete signatures let the Zentaji backend compile their indirect calls.

The production Forge/native Zentaji console-grid check verifies exact characters,
styles and cursor, callback order, unregister/reset, wrap/scroll and 10001 bytes
without loss. The A64 emitted check also passes four capture rotations, RLE CRCs,
45150 lossless bytes and styled terminal operations. These are model/component
proofs. The Zentaji monitor's resident graphical prompt is still unfinished.

The Zentaji serial transport feeds these shared screen and auxiliary taps only
after an accepted write. Diverted background messages and refused writes never
enter the taps. Screen styles remain beside bytes; the prompt selects its style
through the shared command hooks without changing serial output. Both taps stay
disabled until a consumer activates them. Native transport/model checks cover
25 cases, including independent byte/style streams, bounded overflow and 10001
UART bytes drained into the shared model without loss. ROM boot, storage, native
text, keyboard editing and sleeping input remain qualified in the counted monitor.
These taps prepare the renderer connection; they do not enable a graphical prompt.

@SECTION Evidence and remaining work

Acceptance runs the shipped native ASM-built Zentaji tools against explicit
instruction effects, ABI boundaries, bytes, pixels and application behavior.
Python helpers write fixtures, inspect native state or calculate independent
expected data; they do not execute a second CPU/device machine.

The established multi-target host Forge build retains its C backend. The
Zentaji emulator, assembler and focused native tools use the ASM backend only.
The planned built-in self-hosted Forge targets only Zentaji and remains unfinished.

Windows and Linux component proofs have explicit scopes. Full Linux acceptance,
visible/physical input, rumble and idle-host cost calibration remain owed;
see `Zentaji/README.md` for checks and boundaries.
