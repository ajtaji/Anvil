# CSD output into a Pi 4 Vulkan vertex buffer: ownership review

Status: **design and desk audit only**. The two-workgroup CSD diagnostic in this directory passed on Pi 4, proving its `32 × 144`-byte output and guards. It wrote to fixed RAM after installing its own V3D page table. It did **not** write into an Anvil `VkBuffer`, run under Neon's page table, or feed a Vulkan vertex fetch. No renderer or board change follows from this review.

## Smallest physical handoff

The Pi 4 Vulkan backend's heap is the page-aligned offscreen window supplied by `AnvilVkV3dWindow`; Neon has already identity-mapped that window for V3D (`vk_v3d_backend.pi4:84–101, 131–147`). `vkAllocateMemory` suballocates it on 4096-byte boundaries (`vk_memory.pbi:118–163, 199–235`). A bound vertex buffer resolves to `avkHeapBase + avkMemOffset[memory] + avkBufMemOffset[buffer]` (`vk_pipeline.pbi:498–535`). `vkMapMemory` returns the same host address without a shadow copy (`vk_memory.pbi:350–403`). The draw closure resolves that very allocation into `avkFlightBinding[idx]\base` and retains both the buffer and its memory until the Vulkan submission completes (`vk_pipeline.pbi:3649–3667, 3755–3763, 3809–3816`). The Pi 4 draw backend checks that the vertex range stays inside the mapped window and cleans the GPU-read span before binning (`vk_v3d_backend.pi4:1169–1185, 1313–1349, 1762–1798`).

Therefore a **Pi 4-specific diagnostic** can reverse the old fixed-output arrangement: create a `VK_BUFFER_USAGE_VERTEX_BUFFER_BIT` buffer, allocate and bind its memory at offset zero, resolve its address, and pass that address to `V3dCsdOutput`. CSD writes directly into the resource the Vulkan vertex fetch will read. This is not an external-memory import and does not require a CPU copy. Anvil's public Vulkan surface does not provide external-memory import, a compute shader pipeline, or a stage/access barrier for an outside CSD producer; `AnvilVkBufferAddress` and the identity-map fact are internal/backend-specific, not portable Vulkan contracts (`vk_pipeline.pbi:449–503`; `vk_v3d_backend.pi4:84–101`). No generic Vulkan or other-board code should assume a host pointer is a GPU virtual address.

## Required ordering and bounds

1. Keep the existing Neon V3D page table installed. Place QPU code, uniforms, compact input records, and the vertex buffer **inside the existing mapped offscreen heap** using distinct live allocations. The fixed `0x03000000` code/input/output addresses and `V3dMmuInit` from the RAM proof cannot be reused in a Vulkan session (`vulkanNeonParticleCsdTwoGroupProof.pi4:14–32, 214–230`). A standalone Vulkan-buffer diagnostic must verify each address and complete extent against `AnvilVkV3dWindow` before CSD submit.
2. Use one dedicated vertex allocation for a whole CSD batch. For `P` particles, `G = (P + 15) / 16`, input capacity `G × 16 × 32`, output capacity `G × 16 × 144`, and visible Vulkan draw count `P × 6`. Require `1 ≤ G ≤ 65535`, `P ≤ 20992` (current Chrome vertex-quad ceiling), `G × 16 × 144 ≤ VkBuffer.size`, and every addition to remain below the 32-bit V3D address limit. For 10,000 particles, `G = 625`, input is 320,000 bytes, and output is 1,440,000 bytes. A 16-lane output group is 2304 bytes, exactly 36 cache lines, so the padded output extent remains 64-byte aligned. The buffer's 4096-byte-aligned base prevents sharing a cache line with another allocation. Fill or otherwise safely define the final group's unused compact records; draw only `P × 6` vertices.
3. Before CSD, ensure the prior Vulkan fence has completed and no other V3D job is active. Publish CPU-written code, uniforms, and input. Set `V3dCsdOutput` to the dedicated buffer address and full padded output extent, submit CSD, and require successful `V3dCsdWait(100000)` **and** `V3dCsdCleanResult() = #V3D_OK`. The CSD submit helper cleans/invalidate ARM output and invalidates V3D caches; its wait cleans GPU write-combiner/L2T and orders writes before later reads (`v3d.pi4:4494–4604, 4605–4700`). Do not read back or copy the vertices on the normal path.
4. Bind that same live `VkBuffer` with byte offset zero, record a non-indexed draw with stride 24 and `firstVertex = 0`, then submit Vulkan only after CSD completion. The current draw path requires `(firstVertex + vertexCount) × stride` to fit the buffer (`vk_pipeline.pbi:2719–2735`). Its submit path retains the buffer/memory and refreshes the vertex cache range before V3D binning. Wait for the Vulkan fence before CSD reuses or frees the allocation. The current Chrome worker binds its one shared vertex buffer at frame begin (`neon_vk_chrome.pi4:1661–1689`), so using a dedicated particle buffer there would require a worker bind/restore and lifecycle change; that is outside this diagnostic task.

## Gates before implementation

The existing two-group proof establishes indexing and byte-exact expansion only. It does not prove the shared page-table handoff, a CSD write to a live Vulkan allocation, or a subsequent vertex fetch. The next isolated board diagnostic should allocate a small Vulkan vertex buffer within the Neon-mapped heap, run two CSD groups into it, check exact bytes and guard space, submit one non-indexed Vulkan draw from that buffer, and compare pixels. Keep both submissions synchronous and under the supervisor's deadman. No production speed claim follows until a 10,000-particle profile measures the complete prepare/CSD/draw/end path.

The present 32-byte compact record and QPU program encode axis-aligned x/y corners only. Chrome's current particle path also handles camera transforms and rotation (`neon_vk_particles.pi4:379–425`); full replacement needs either a proven four-corner record/shader or a correctly ordered CPU fallback. A CSD timeout or GPU cache-clean failure may leave writes in flight; `V3dCsdWait` reports the fault but does not cancel the job. A production bridge must treat that as device loss and prevent reuse/free of its buffer until the engine is reset or known idle. Finally, Vulkan's resource-retention counts cover Vulkan submissions, not this external CSD interval. Any reusable bridge must own the buffer and memory across **both** intervals, rather than exposing a raw address to arbitrary callers. These are the reasons no runtime integration was made here.
